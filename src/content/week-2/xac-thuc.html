Hai câu hỏi khác nhau

Hình dung toà nhà văn phòng. Ở cổng, bảo vệ kiểm tra thẻ nhân viên: bạn là ai? Đó là xác thực (authentication, viết tắt AuthN). Lên tới tầng 5, cửa phòng kế toán chỉ mở cho người của phòng kế toán: bạn được vào đâu? Đó là phân quyền (authorization, viết tắt AuthZ).

Thông tin xác thực đi trong request thế nào

Vì HTTP không nhớ gì giữa các request, mỗi request phải tự mang theo bằng chứng. Cách chuẩn là header Authorization:

GET /books HTTP/1.1
Authorization: Bearer key-ghi-cua-ban

Chữ Bearer nghĩa là "ai cầm token này thì được coi là chủ của nó", giống vé xem phim. Vì vậy token phải được giữ bí mật, chỉ gửi qua HTTPS, và không bao giờ đưa vào URL vì URL hay bị ghi vào log.

Bài Thứ Năm: thêm API key vào API sách

Quy tắc: GET là công khai. POST, PATCH, DELETE cần key. Có hai loại key: read (chỉ đọc) và write (được ghi). Thiếu hoặc sai key thì 401. Key read mà gọi lệnh ghi thì 403.

Tách thành hai middleware, mỗi cái trả lời đúng một câu hỏi:

import { createMiddleware } from 'hono/factory';
import { timingSafeEqual } from 'node:crypto';

type Role = 'read' | 'write';
export type Env = { Variables: { role: Role } };

// Bài luyện: đọc key từ biến môi trường thay vì viết cứng
const KEYS: Record<string, Role> = { 'key-doc': 'read', 'key-ghi': 'write' };

function same(a: string, b: string) {
  const x = Buffer.from(a), y = Buffer.from(b);
  return x.length === y.length && timingSafeEqual(x, y);
}

// Câu hỏi 1: bạn là ai?
export const requireKey = createMiddleware<Env>(async (c, next) => {
  const header = c.req.header('authorization') ?? '';
  const token = header.startsWith('Bearer ') ? header.slice(7) : '';
  const found = Object.entries(KEYS).find(([k]) => same(k, token));
  if (!found) {
    c.header('WWW-Authenticate', 'Bearer');
    return c.json({ error: { code: 'UNAUTHENTICATED', message: 'Thiếu hoặc sai API key' } }, 401);
  }
  c.set('role', found[1]);
  await next();
});

// Câu hỏi 2: bạn có được ghi không?
export const requireWrite = createMiddleware<Env>(async (c, next) => {
  if (c.get('role') !== 'write') {
    return c.json({ error: { code: 'FORBIDDEN', message: 'Key này chỉ được đọc' } }, 403);
  }
  await next();
});

app.post('/books', requireKey, requireWrite, createBook);

Vì sao dùng timingSafeEqual

So sánh chuỗi bằng === dừng ngay ở ký tự sai đầu tiên. Kẻ tấn công đo thời gian phản hồi có thể đoán dần từng ký tự của key: ký tự đúng làm phép so sánh lâu hơn một chút. timingSafeEqual luôn so hết, mất thời gian như nhau dù sai ở đâu. Nó yêu cầu hai chuỗi cùng độ dài, nên phải kiểm tra độ dài trước.

Phân quyền phải chạy ở mọi request

Lỗi bảo mật kinh điển: kiểm tra đăng nhập rồi thôi. Giáo viên A đăng nhập hợp lệ, gọi GET /invoices/<id của lớp B>, và server trả hóa đơn vì "đã đăng nhập rồi mà". Lỗi này có tên là IDOR (Insecure Direct Object Reference). Cách chặn: mọi truy vấn dữ liệu đều lọc theo chủ sở hữu.

// Sai: chỉ tìm theo id
const invoice = await store.findInvoice(id);

// Đúng: tìm theo id VÀ giáo viên đang đăng nhập
const invoice = await store.findInvoice({ id, teacherId: c.get('teacherId') });
if (!invoice) throw new AppError(404, 'NOT_FOUND', 'Không có hóa đơn');

Lưu bí mật đúng cách

  • Không viết key, mật khẩu vào code hay commit lên Git. Đặt trong biến môi trường, validate bằng zod khi khởi động.
  • File .env phải có trong .gitignore. Commit một file .env.example chỉ có tên biến, không có giá trị.
  • Mật khẩu người dùng không bao giờ lưu nguyên văn. Lưu bản băm bằng thuật toán chậm như scrypt (có sẵn trong node:crypto), bcrypt hoặc argon2.

Bút đỏ: những câu nghe đúng mà sai

"Đã đăng nhập thì cho xem dữ liệu."Sai. Đăng nhập chỉ trả lời "bạn là ai". Mỗi truy vấn vẫn phải kiểm tra dữ liệu đó có phải của bạn không.

"Gửi token qua query string ?token=... cho tiện."Không. URL bị ghi vào log, lịch sử trình duyệt và header Referer. Dùng header Authorization.

"Ẩn nút Xoá ở giao diện là đủ chặn người không có quyền."Sai. Ai cũng gọi thẳng API được. Phân quyền phải nằm ở server.

Câu hỏi phỏng vấn

Authentication và authorization khác nhau thế nào?

Authentication xác định bạn là ai, bằng mật khẩu, token hay OTP. Authorization quyết định bạn được làm gì, dựa trên vai trò hay quyền sở hữu. Authentication luôn chạy trước. Sai ở authentication trả 401, sai ở authorization trả 403.

IDOR là gì và phòng thế nào?

Là khi server dùng id do client gửi để lấy dữ liệu mà không kiểm tra người gọi có quyền với dữ liệu đó không. Ví dụ đổi id trên URL là xem được hóa đơn của người khác. Phòng bằng cách mọi truy vấn đều lọc theo chủ sở hữu, và có test cho trường hợp người A truy cập dữ liệu của người B.

Vì sao so sánh token không nên dùng ===?

Vì === dừng ở ký tự sai đầu tiên, nên thời gian phản hồi tiết lộ bao nhiêu ký tự đầu đã đúng. Đó là timing attack. Dùng hàm so sánh thời gian hằng như crypto.timingSafeEqual.

Session cookie và JWT khác nhau thế nào?

Với session, server lưu trạng thái phiên và cookie chỉ chứa mã phiên, nên thu hồi dễ bằng cách xoá phiên. JWT tự chứa thông tin và chữ ký, server không cần lưu gì, hợp khi nhiều dịch vụ cùng kiểm tra, nhưng khó thu hồi trước khi hết hạn. Với web app một server như công cụ thu học phí, session đơn giản và an toàn hơn.
