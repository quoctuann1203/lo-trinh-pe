Trong một câu

Test (kiểm thử tự động) là đoạn code gọi code của bạn với một đầu vào cố định rồi so kết quả với điều bạn mong đợi. Khớp thì qua, không khớp thì báo đỏ, và máy làm việc đó trong vài giây mỗi lần bạn sửa code.

Hình dung giáo viên chấm bài có sẵn đáp án. Thay vì tự đọc từng bài, cô đưa máy chấm: đặt bài vào, máy so với đáp án và báo câu nào sai.

Một bài test trông thế nào

import { test, expect } from 'vitest';
import { tinhHocPhi } from './hoc-phi';

test('8 buổi, 150.000đ mỗi buổi thì học phí là 1.200.000đ', () => {
  expect(tinhHocPhi(8, 150_000)).toBe(1_200_000);
});

Tên test viết như một câu mô tả hành vi. Khi nó hỏng, chỉ đọc tên là biết hành vi nào bị vỡ.

Vì sao phải viết test

  • Dám sửa code. Tuần sau bạn đổi cách lưu từ Map sang database. Có test, bạn chạy một lệnh và biết ngay 5 endpoint còn đúng không. Không có test, bạn phải gõ lại 15 lệnh curl bằng tay.
  • Bắt lỗi sớm và rẻ. Lỗi tính sai học phí bị test bắt trên máy bạn tốn 1 phút. Cùng lỗi đó bị phụ huynh phát hiện thì tốn cả uy tín.
  • Test là tài liệu sống. Đọc test của POST /books là biết API chấp nhận gì, từ chối gì, trả mã nào. Và tài liệu này không bao giờ cũ, vì nó cũ là nó hỏng.

Từ khoá cần biết

Test case
Một bài test: một tình huống, một kết quả mong đợi.
Assertion (expect)
Câu khẳng định trong test, ví dụ expect(x).toBe(5). Sai là test đỏ.
Unit test
Test một hàm hoặc một module, tách khỏi phần còn lại.
Integration test
Test nhiều phần chạy cùng nhau, ví dụ gửi request vào app rồi kiểm tra response.
E2E test
Test cả hệ thống như người dùng thật: mở trình duyệt, bấm nút.
Ranh giới (edge case)
Giá trị ở mép quy tắc: 0, 1, chuỗi rỗng, đúng giới hạn và vượt giới hạn một chút.
Regression
Lỗi đã sửa rồi lại quay lại. Mỗi bug sửa xong nên có một test chặn nó.
TDD
Viết test trước, thấy nó đỏ, rồi mới viết code cho nó xanh.

Một lần chạy test diễn ra thế nào

  1. Bạn gõ npm test. Trình chạy test (Vitest) tìm mọi file tên *.test.ts.
  2. Mỗi test chạy riêng: chuẩn bị dữ liệu, gọi code, kiểm tra kết quả bằng expect.
  3. Báo kết quả: test nào qua thì xanh, test nào hỏng thì đỏ kèm "mong đợi gì, nhận được gì".
  4. Chế độ theo dõi: bạn lưu file là test liên quan tự chạy lại.

Hình ảnh quen thuộc là kim tự tháp test: nhiều unit test ở đáy vì chúng nhanh và rẻ, ít integration hơn ở giữa, rất ít E2E ở đỉnh vì chúng chậm và dễ hỏng vặt. Với một API như API sách, integration test qua app.request() cho nhiều giá trị nhất trên mỗi dòng code test, vì nó kiểm tra đúng thứ client nhìn thấy mà vẫn chạy rất nhanh.

Nên test cái gì

Đừng hỏi "dòng code này đã được test chưa". Hãy hỏi "nếu hành vi này hỏng, ai bị ảnh hưởng?". Ưu tiên:

  1. Hành vi chính: tạo được sách, tính đúng học phí.
  2. Ranh giới: 0 buổi, 1 buổi, giảm giá 100%, chuỗi rỗng, đúng 200 ký tự và 201 ký tự.
  3. Đường lỗi: mỗi mã 4xx bạn hứa trả, và một test cho nhánh 500.
  4. Lỗi đã từng xảy ra: mỗi bug bạn sửa đều nên có một test để nó không quay lại. Ví dụ bẫy PATCH làm mất tags ở tuần 1.

Không cần test: code của thư viện (zod đã được test bởi tác giả zod), getter và setter tầm thường, và chi tiết bên trong mà client không nhìn thấy.

Cấu trúc một test: Chuẩn bị, Làm, Kiểm tra

test('PATCH chỉ đổi title thì tags giữ nguyên', async () => {
  // Chuẩn bị (Arrange): tạo dữ liệu ban đầu
  const created = await createBook({ title: 'Dế Mèn', tags: ['thiếu nhi'] });

  // Làm (Act): một hành động duy nhất cần kiểm tra
  const res = await req('PATCH', `/books/${created.id}`, { title: 'Dế Mèn (tái bản)' });

  // Kiểm tra (Assert): kết quả có đúng không
  expect(res.status).toBe(200);
  expect((await res.json()).tags).toEqual(['thiếu nhi']);
});

Mỗi test kiểm tra một hành vi. Test nào kiểm tra năm thứ cùng lúc, khi hỏng bạn phải đọc cả test để biết cái gì vỡ.

Test tốt có bốn tính chất

  • Nhanh: cả bộ chạy trong vài giây, để bạn chạy nó liên tục.
  • Độc lập: chạy riêng hay chạy chung, theo thứ tự nào cũng ra cùng kết quả. Vì vậy phải reset dữ liệu trước mỗi test.
  • Ổn định: không phụ thuộc giờ hệ thống, mạng, hay may rủi. Test lúc qua lúc hỏng (gọi là flaky) còn tệ hơn không có test, vì mọi người sẽ học cách lờ màu đỏ đi.
  • Kiểm tra hành vi, không kiểm tra cách làm: test gọi API và xem response, không đi soi biến bên trong. Như vậy bạn đổi cách cài đặt mà test vẫn đúng.

TDD: viết test trước

Test-Driven Development là vòng lặp ba bước: Đỏ (viết một test cho hành vi chưa có, chạy thấy hỏng), Xanh (viết code tối thiểu để test qua), Dọn (sửa code cho đẹp, test vẫn xanh). Bạn không cần làm TDD cho mọi thứ. Nhưng hôm Thứ Năm, khi thêm API key, hãy thử: viết test 401 và 403 trước, thấy chúng đỏ, rồi mới viết middleware. Cảm giác thấy test chuyển từ đỏ sang xanh cho bạn biết chắc test đó thật sự kiểm tra được thứ gì.

Làm thử: liệt kê test trước khi viết code

Hàm tinhHocPhi(soBuoi, giaMoiBuoi, giamGiaPhanTram) tính học phí một tháng. Chưa cần viết code, chỉ viết ra giấy danh sách tên test theo bốn nhóm ở mục "Nên test cái gì". Rồi so với gợi ý:

NhómTên test gợi ý
Hành vi chính8 buổi, 150.000đ, không giảm thì 1.200.000đ
Ranh giới0 buổi thì 0đ; giảm 100% thì 0đ; giảm 10% của 1.200.000đ thì 1.080.000đ
Đường lỗiSố buổi âm thì ném lỗi; giảm giá trên 100% thì ném lỗi
Lỗi đã từng xảy raSố tiền lẻ được làm tròn về đồng, không còn số thập phân

Bài Vitest ngay sau sẽ biến danh sách này thành test chạy được.

Bút đỏ: những câu nghe đúng mà sai

"Coverage 100% nghĩa là không còn bug."Sai. Coverage chỉ nói dòng code đã được chạy, không nói kết quả đã được kiểm tra đúng. Một test không có expect vẫn làm coverage tăng.

"Test làm chậm tiến độ."Chỉ chậm ở ngày đầu. Từ lần sửa code thứ hai trở đi, test tiết kiệm thời gian kiểm tra tay.

"Càng nhiều E2E test càng chắc."Không. E2E chậm và hay hỏng vặt. Dùng ít, cho những luồng quan trọng nhất như thu tiền.

Tự kiểm tra

Tự trả lời trước, rồi mới bấm mở đáp án.

Kiểm tra POST /books trả 201 bằng app.request() là loại test gì?

Integration test: route, validate, xử lý lỗi và kho dữ liệu chạy cùng nhau, nhưng không cần trình duyệt.

Vì sao kim tự tháp test có nhiều unit test và rất ít E2E?

Unit test nhanh, rẻ, ít hỏng vặt. E2E chậm, dễ hỏng vì lý do ngoài code, nên chỉ để cho vài luồng quan trọng nhất.

Có cần viết test kiểm tra zod bắt được chuỗi rỗng không?

Không cần test bản thân zod. Nên test hành vi của API: gửi chuỗi rỗng thì API trả 422 đúng định dạng lỗi.

Câu hỏi phỏng vấn

Unit test, integration test và E2E test khác nhau thế nào?

Unit test kiểm tra một đơn vị nhỏ tách riêng, chạy rất nhanh. Integration test kiểm tra nhiều phần chạy cùng nhau, ví dụ gửi request vào app và kiểm tra response qua cả route, validate và xử lý lỗi. E2E kiểm tra cả hệ thống như người dùng thật, chậm nhất và dễ hỏng vặt nhất. Thường nên có nhiều unit, vừa phải integration, ít E2E.

Bạn quyết định test cái gì thế nào?

Theo rủi ro: hành vi chính, các ranh giới, mọi đường lỗi mà API hứa trả, và mọi bug đã từng xảy ra. Không test code thư viện hay chi tiết bên trong. Mình test hành vi mà client nhìn thấy, để đổi cách cài đặt không làm hỏng test.

Coverage bao nhiêu là đủ?

Không có con số thần kỳ. Coverage cao mà test không kiểm tra kết quả thì vô nghĩa. Mình dùng coverage để tìm chỗ chưa test, rồi tự hỏi chỗ đó hỏng thì có sao không. Với logic tiền bạc như tính học phí, mình muốn gần 100% kèm test ranh giới.

Flaky test là gì? Xử lý thế nào?

Là test lúc qua lúc hỏng dù code không đổi, thường do phụ thuộc thời gian thật, thứ tự chạy, dữ liệu chung giữa các test, hoặc mạng. Xử lý bằng cách reset dữ liệu trước mỗi test, giả lập thời gian, và mock các lời gọi ra ngoài. Không bao giờ chấp nhận "chạy lại là qua".

Nhớ 3 ý

  1. Test là code so kết quả thật với kết quả mong đợi; nhờ nó bạn dám sửa code.
  2. Ưu tiên test hành vi chính, ranh giới, đường lỗi và các bug đã từng gặp.
  3. Mỗi test có ba phần: chuẩn bị, làm, kiểm tra; tên test là một câu mô tả hành vi.
