Trong một câu

Khởi tạo repo là dựng bộ khung ban đầu cho dự án sản phẩm: tạo project Next.js, cài công cụ test, sắp thư mục, viết test đầu tiên, rồi đẩy lên GitHub. Từ đây mỗi thay đổi đều được lưu lịch sử và kiểm tra.

Hình dung xây nhà: trước khi chọn màu sơn, phải đổ móng, kéo điện nước. Repo là phần móng đó; làm đúng từ đầu thì về sau xây thêm tầng nào cũng không phải đập ra làm lại.

Vì sao làm việc này ngay cả khi đổi ý tưởng

Dù quyết định Thứ Bảy là làm tiếp hay đổi hướng, bạn vẫn cần một repo sản phẩm có nền móng đúng: chạy được, test được, build được. Nếu đổi ý tưởng, chỉ cần đổi tên repo. Phần nền móng bên dưới giống hệt.

Từ khoá cần biết

Repo (repository)
Thư mục dự án được Git theo dõi lịch sử thay đổi.
Git
Công cụ lưu lịch sử code: mỗi lần lưu là một commit.
GitHub
Trang web lưu repo Git trên mạng, để sao lưu và làm việc nhóm.
Next.js
Framework React làm được cả giao diện lẫn phần server trong cùng một dự án.
create-next-app
Lệnh tạo sẵn project Next.js với cấu hình chuẩn.
CI
Continuous Integration: máy chủ tự chạy test mỗi lần bạn đẩy code lên.
.gitignore
File liệt kê thứ không đưa lên Git, như node_modules và .env.

Làm thử, bước 1: tạo project

npx create-next-app@latest hocphi --ts --app --no-tailwind --eslint --src-dir --import-alias "@/*" --use-npm --yes
cd hocphi
npm run dev        # mở http://localhost:3000

Ý nghĩa các cờ: --ts dùng TypeScript; --app dùng App Router; --src-dir đặt code trong src/; --import-alias "@/*" cho phép viết import x from '@/lib/x' thay vì '../../lib/x'. Bỏ --no-tailwind nếu bạn muốn dùng Tailwind.

Next.js 16 khác nhiều so với các video và bài viết cũ. Ba điểm bạn sẽ gặp ngay:

  • Template tạo sẵn file AGENTS.md, nhắc rằng API đã thay đổi và tài liệu đúng phiên bản nằm trong node_modules/next/dist/docs/. Khi nhờ Claude Code viết code, đó chính là tài liệu nó nên đọc.
  • params của page là một Promise: viết const { id } = await params.
  • next.config.ts có thể bật sẵn cacheComponents. Đọc docs/01-app/02-guides/ về cache trước khi viết phần đọc dữ liệu.

Bước 2: cài Vitest theo hướng dẫn chính thức của Next.js

# Template cài @types/node bản 20, còn Vitest 5 cần bản 22 hoặc từ 24 trở lên.
# Không nâng trước thì npm báo lỗi ERESOLVE ở lệnh dưới.
npm install -D @types/node@24
npm install -D vitest @vitejs/plugin-react jsdom @testing-library/react @testing-library/dom vite-tsconfig-paths

Gặp lỗi ERESOLVE, đừng vội thêm --force hay --legacy-peer-deps. Đọc dòng "Could not resolve dependency" trong thông báo lỗi: nó cho biết gói nào cần phiên bản nào. Thường chỉ cần nâng đúng gói đó.

// vitest.config.mts
import { defineConfig } from 'vitest/config';
import react from '@vitejs/plugin-react';
import tsconfigPaths from 'vite-tsconfig-paths';

export default defineConfig({
  plugins: [tsconfigPaths(), react()],
  test: { environment: 'jsdom' },
});

Thêm script vào package.json:

"scripts": {
  "dev": "next dev",
  "build": "next build",
  "start": "next start",
  "lint": "eslint",
  "typecheck": "tsc --noEmit",
  "test": "vitest",
  "test:run": "vitest run"
}

Lưu ý từ tài liệu Next.js: Vitest chưa hỗ trợ async Server Component. Component đồng bộ thì test được. Trang async thì dùng E2E test sau này. Vì vậy logic nghiệp vụ nên nằm trong hàm thuần, tách khỏi component, để test dễ.

Bước 3: cấu trúc thư mục cho một sản phẩm thật

src/
  app/                 ← route: page, layout, route handler. Mỏng, chỉ nối các phần lại
  components/          ← component giao diện
  lib/
    domain/            ← logic nghiệp vụ thuần: tính học phí, khớp giao dịch với hóa đơn
      hoc-phi.ts
      hoc-phi.test.ts  ← test đặt cạnh code
    validation/        ← schema zod dùng chung cho form và API
validation/            ← giả thuyết, ghi chép phỏng vấn, decision.md từ tuần 1 và 2
.env.example           ← tên các biến môi trường, không có giá trị

Nguyên tắc: logic tiền bạc nằm trong lib/domain, không phụ thuộc Next.js, React hay database. Đó là phần quan trọng nhất của công cụ thu học phí, nên nó phải dễ test nhất.

Bước 4: test đầu tiên

Chuyển hàm tinhHocPhi từ bài Thứ Ba sang src/lib/domain/hoc-phi.ts, kèm 6 test của nó. Chạy:

npm run test:run     # 6 test qua
npm run typecheck    # không lỗi kiểu
npm run build        # build thành công

Bước 5: đưa lên GitHub

git add -A
git commit -m "chore: khởi tạo Next.js, TypeScript, Vitest"
gh repo create hocphi --private --source=. --push

Đặt repo ở chế độ --private cho tới khi bạn muốn công khai. Kiểm tra .gitignore đã có .env* trước lần commit đầu tiên. Một khi bí mật đã vào lịch sử Git, xoá file đi là chưa đủ.

Tuỳ chọn: CI chạy test mỗi lần push

# .github/workflows/ci.yml
name: CI
on: [push, pull_request]
jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 24
          cache: npm
      - run: npm ci
      - run: npm run lint
      - run: npm run typecheck
      - run: npm run test:run
      - run: npm run build

Từ giờ, mỗi lần push đều có một dấu xanh hoặc đỏ trên GitHub. Đó cũng là thứ người phỏng vấn hay mở ra xem đầu tiên.

"Viết logic tính tiền ngay trong page cho nhanh."Không. Tách vào lib/domain thành hàm thuần. Page async khó test, còn hàm thuần thì test trong vài mili-giây.

"npm báo ERESOLVE thì thêm --force cho xong."Không. --force cài cả những phiên bản không hợp nhau. Đọc lỗi, nâng đúng gói được nhắc tới.

"Commit .env rồi xoá đi ở commit sau là an toàn."Sai. Nó vẫn nằm trong lịch sử Git. Phải đổi ngay khoá bị lộ.

Tự kiểm tra

Tự trả lời trước, rồi mới bấm mở đáp án.

Vì sao không đưa file .env lên GitHub?

Nó chứa bí mật như mật khẩu database và API key. Ai xem được repo là có bí mật.

Test đầu tiên của repo chỉ kiểm tra một hàm rất đơn giản. Nó có ích gì?

Nó chứng minh bộ công cụ test đã chạy đúng. Từ đây thêm test mới chỉ là viết thêm file.

CI chạy test mỗi lần push giúp gì khi bạn làm một mình?

Bắt lỗi khi bạn quên chạy test trên máy, và cho thấy code chạy được trên một máy sạch, không chỉ máy của bạn.

Câu hỏi phỏng vấn

Bạn tổ chức thư mục một project Next.js thế nào?

Route trong app/ giữ mỏng, chỉ nối dữ liệu với giao diện. Component giao diện trong components/. Logic nghiệp vụ là hàm thuần trong lib/domain, không phụ thuộc framework, có test đặt cạnh. Schema zod dùng chung cho form và API. Như vậy phần quan trọng nhất dễ test nhất và không bị khoá vào framework.

Server Component và Client Component khác nhau thế nào?

Server Component chạy trên server, đọc dữ liệu trực tiếp được và không gửi JavaScript của nó xuống trình duyệt. Client Component, đánh dấu bằng 'use client', chạy cả trong trình duyệt, dùng được state, effect và sự kiện. Mặc định trong App Router là Server Component. Chỉ phần nào cần tương tác mới là Client Component.

CI là gì, bạn cho nó chạy những gì?

Continuous Integration: mỗi lần push hoặc mở pull request, một máy chủ tự chạy các bước kiểm tra. Mình cho chạy lint, kiểm tra kiểu, test và build. Nếu bước nào đỏ thì không merge. Nó bắt lỗi trước khi lỗi vào nhánh chính.

Nhớ 3 ý

  1. Repo sản phẩm cần chạy được, test được, build được ngay từ ngày đầu.
  2. Thứ tự: tạo project, cài Vitest, sắp thư mục, test đầu tiên, đẩy lên GitHub.
  3. Bí mật không lên Git; CI chạy test giúp bạn mỗi lần push.
