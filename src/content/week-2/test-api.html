Trong một câu

Test API là viết test gửi request thật vào app của bạn (không cần mở server) rồi kiểm tra mã trạng thái và body trả về, đúng như bạn vẫn làm bằng curl, nhưng máy làm và chạy lại được mỗi lần sửa code.

Hình dung một "khách hàng bí mật" được thuê đi thử quán: gọi đủ mọi món, cố tình gọi món không có, trả tiền sai, rồi ghi lại quán phản ứng ra sao. Bộ test API là khách hàng bí mật đó, đến thử quán mỗi lần bạn thay đổi thực đơn.

Vì sao test qua API thay vì test từng hàm

Người dùng API của bạn (front-end, app di động) chỉ thấy request và response. Test ở mức đó kiểm tra đúng thứ họ thấy: route, validate, xử lý lỗi và kho dữ liệu cùng lúc. Với Hono, app.request() gọi thẳng vào app trong bộ nhớ, nên test vẫn chạy rất nhanh mà không phải mở cổng hay chờ mạng.

Từ khoá cần biết

app.request()
Hàm của Hono gửi một request vào app ngay trong test, trả về Response như fetch.
Hàm trợ giúp (helper)
Hàm nhỏ bạn tự viết để khỏi lặp lại phần giống nhau, ví dụ gửi JSON kèm API key.
Fixture
Dữ liệu mẫu dùng lại trong nhiều test, ví dụ một cuốn sách hợp lệ.
beforeEach
Chạy trước mỗi test, thường để xoá dữ liệu cho mỗi test bắt đầu sạch.
Độ phủ (coverage)
Phần trăm dòng code đã chạy qua khi test. Dùng để tìm nhánh chưa ai thử.
Mutation testing (tay)
Cố tình làm hỏng code để xem bộ test có bắt được không.

Một test API chạy thế nào

  1. Dọn dữ liệu trong beforeEach để test không phụ thuộc nhau.
  2. Gửi request bằng app.request('/books', { method: 'POST', ... }).
  3. Kiểm tra mã trạng thái: expect(res.status).toBe(201).
  4. Kiểm tra body bằng await res.json(), và nếu cần, gọi thêm một request để xác nhận dữ liệu đã thật sự đổi.

Từ curl sang test

Ở tuần 1 bạn kiểm tra API bằng 15 lệnh curl, đọc mã trạng thái bằng mắt. Test tự động làm đúng việc đó, nhưng máy đọc thay bạn, chạy hết trong chưa tới một giây, và chạy lại được mỗi lần bạn sửa code.

app.request() nhận đường dẫn và các tuỳ chọn giống fetch, rồi trả về một Response chuẩn. Đó là lý do tuần 1 bạn tách app.ts khỏi index.ts: test import app mà không khởi động server.

Đặt file test ở đâu

Đặt cạnh code: src/books.test.ts. Template Hono dùng "module": "NodeNext", nên import trong test vẫn ghi đuôi .js như code thường, Vitest tự hiểu. Thêm vào tsconfig.json để npm run build không biên dịch file test vào dist/:

"exclude": ["node_modules", "src/**/*.test.ts"]

Làm thử, bước 1: một hàm trợ giúp gửi request

// src/test-helpers.ts
import { app } from './app.js';

export const KEY_WRITE = 'key-ghi';
export const KEY_READ = 'key-doc';

export function req(method: string, path: string, body?: unknown, key?: string) {
  const headers: Record<string, string> = {};
  if (body !== undefined) headers['Content-Type'] = 'application/json';
  if (key) headers['Authorization'] = `Bearer ${key}`;
  const raw = typeof body === 'string' ? body : JSON.stringify(body);
  return app.request(path, { method, headers, body: body === undefined ? undefined : raw });
}

export const validBook = {
  title: 'Dế Mèn phiêu lưu ký',
  author: 'Tô Hoài',
  isbn: '9786040000001',
  publishedYear: 1941,
  tags: ['thiếu nhi'],
};

export async function createBook(overrides: Partial<typeof validBook> = {}) {
  const res = await req('POST', '/books', { ...validBook, ...overrides }, KEY_WRITE);
  return res.json();
}

Nhận body dạng chuỗi cho phép bạn test JSON hỏng bằng cách truyền thẳng '{oops'.

Bước 2: mỗi endpoint một nhóm test

// src/books.test.ts
import { beforeEach, describe, expect, test, vi } from 'vitest';
import { resetStore } from './book-store.js';
import { createBook, KEY_READ, KEY_WRITE, req, validBook } from './test-helpers.js';

beforeEach(() => resetStore());

describe('POST /books', () => {
  test('dữ liệu hợp lệ → 201, có Location, tags giữ nguyên', async () => {
    const res = await req('POST', '/books', validBook, KEY_WRITE);
    expect(res.status).toBe(201);
    const body = await res.json();
    expect(res.headers.get('Location')).toBe(`/books/${body.id}`);
    expect(body).toMatchObject({ title: validBook.title, tags: ['thiếu nhi'] });
  });

  test('ISBN trùng → 409 ISBN_TAKEN', async () => {
    await createBook();
    const res = await req('POST', '/books', validBook, KEY_WRITE);
    expect(res.status).toBe(409);
    expect((await res.json()).error.code).toBe('ISBN_TAKEN');
  });

  test('JSON hỏng → 400 INVALID_JSON', async () => {
    const res = await req('POST', '/books', '{oops', KEY_WRITE);
    expect(res.status).toBe(400);
  });

  test.each([
    { field: 'title', value: '' },
    { field: 'publishedYear', value: 3000 },
    { field: 'isbn', value: '123' },
  ])('$field = $value → 422, lỗi nằm ở đúng trường', async ({ field, value }) => {
    const res = await req('POST', '/books', { ...validBook, [field]: value }, KEY_WRITE);
    expect(res.status).toBe(422);
    expect((await res.json()).error.details.fieldErrors).toHaveProperty(field);
  });
});

Bước 3: test riêng cho từng bẫy đã biết

describe('PATCH /books/:id', () => {
  test('chỉ gửi title → title đổi, tags giữ nguyên', async () => {
    const book = await createBook();
    const res = await req('PATCH', `/books/${book.id}`, { title: 'Dế Mèn (tái bản)' }, KEY_WRITE);
    expect(res.status).toBe(200);
    expect(await res.json()).toMatchObject({ title: 'Dế Mèn (tái bản)', tags: ['thiếu nhi'] });
  });

  test('body rỗng {} → 422', async () => {
    const book = await createBook();
    expect((await req('PATCH', `/books/${book.id}`, {}, KEY_WRITE)).status).toBe(422);
  });
});

Đây chính là bẫy .partial() với .default() của tuần 1. Một bug đã từng xảy ra thì phải có test giữ cửa để nó không quay lại.

Bước 4: test 401, 403 và 500

describe('xác thực', () => {
  test('ghi mà không có key → 401, kèm WWW-Authenticate', async () => {
    const res = await req('POST', '/books', validBook);
    expect(res.status).toBe(401);
    expect(res.headers.get('WWW-Authenticate')).toBe('Bearer');
  });

  test('key chỉ đọc mà ghi → 403', async () => {
    expect((await req('POST', '/books', validBook, KEY_READ)).status).toBe(403);
  });

  test('đọc không cần key → 200', async () => {
    expect((await req('GET', '/books')).status).toBe(200);
  });
});

test('lỗi bất ngờ → 500, không lộ stack, có ghi log', async () => {
  const spy = vi.spyOn(console, 'error').mockImplementation(() => {});
  const res = await req('GET', '/__boom');
  expect(res.status).toBe(500);
  expect(await res.text()).not.toContain('at ');
  expect(spy).toHaveBeenCalled();
  spy.mockRestore();
});

Bước 5: đo độ phủ và lấp chỗ trống

npx vitest run --coverage --coverage.include='src/**/*.ts' --coverage.exclude='src/**/*.test.ts' --coverage.exclude='src/index.ts'

Đọc cột "Uncovered Line #s". Với mỗi dòng chưa được chạy, hỏi: dòng này hỏng thì client thấy gì? Nếu câu trả lời quan trọng, viết thêm test. Bỏ index.ts ra khỏi phép đo vì nó chỉ khởi động server.

Kiểm tra lại chính bộ test

Một test chưa từng thấy đỏ thì chưa chắc đã kiểm tra được gì. Cách thử nhanh: cố tình làm hỏng code, ví dụ đổi 201 thành 200 trong handler POST, chạy test, thấy đúng test đó đỏ, rồi trả lại. Làm vậy với hai hoặc ba chỗ quan trọng nhất.

Bút đỏ: những câu nghe đúng mà sai

"Dùng chung một cuốn sách tạo sẵn cho mọi test cho nhanh."Sai. Test này sửa sách thì test kia hỏng theo, tuỳ thứ tự chạy. Reset kho trong beforeEach, mỗi test tự tạo dữ liệu của nó.

"Chỉ cần kiểm tra mã trạng thái là đủ."Chưa đủ. Kiểm tra thêm phần body quan trọng: error.code, trường bị lỗi, dữ liệu trả về. Hai lỗi khác nhau có thể cùng mã 422.

"Test qua hết rồi, không cần thử làm hỏng code."Nên thử. Test chưa từng đỏ có thể là test không kiểm tra gì cả.

Tự kiểm tra

Tự trả lời trước, rồi mới bấm mở đáp án.

Vì sao mỗi test nên tự tạo dữ liệu nó cần, thay vì dựa vào test chạy trước?

Để test chạy được riêng lẻ, theo thứ tự bất kỳ. Test phụ thuộc nhau thì một cái hỏng kéo theo cả loạt, rất khó tìm nguyên nhân.

Test DELETE /books/:id trả 204. Như vậy đã đủ chưa?

Chưa. Nên gọi tiếp GET /books/:id và mong đợi 404, để chắc sách thật sự đã bị xoá.

Bạn xoá dòng kiểm tra ISBN trùng trong code mà bộ test vẫn xanh. Điều đó nói gì?

Bộ test chưa có test nào cho trường hợp ISBN trùng. Phải thêm test mong đợi 409.

Câu hỏi phỏng vấn

Bạn test một REST API như thế nào?

Mình viết integration test gửi request vào app, với Hono là app.request(), không cần mở cổng. Mỗi endpoint có test cho đường thành công và mọi mã lỗi mà nó hứa trả, kiểm tra cả mã trạng thái, header quan trọng và body. Dữ liệu được reset trước mỗi test để các test độc lập. Logic thuần như tính học phí thì có unit test riêng.

Làm sao để các test không ảnh hưởng nhau?

Mỗi test tự tạo dữ liệu nó cần, và trạng thái chung được reset trong beforeEach: xoá kho trong bộ nhớ, hoặc với database thật thì chạy trong transaction rồi rollback, hay dọn bảng. Không có test nào phụ thuộc vào thứ tự chạy.

Integration test cho API có cần database thật không?

Tuỳ mục tiêu. Kho trong bộ nhớ cho test rất nhanh và đủ để kiểm tra route, validate, xử lý lỗi. Nhưng các ràng buộc của database như khoá duy nhất hay transaction thì chỉ test được với database thật, thường chạy bằng Docker trong CI. Mình sẽ có cả hai: phần lớn chạy nhanh với kho giả, một nhóm nhỏ chạy với database thật.

Nhớ 3 ý

  1. Test API gửi request vào app bằng app.request() và kiểm tra mã lẫn body, không cần mở server.
  2. Mỗi test tự dọn và tự tạo dữ liệu; mỗi bẫy đã biết có một test riêng.
  3. Thử làm hỏng code: test vẫn xanh nghĩa là còn chỗ chưa được kiểm tra.
