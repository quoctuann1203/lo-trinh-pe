Một lỗi của PostgreSQL trông thế nào

Thêm hai cuốn sách cùng ISBN, rồi in ra lỗi mà pg ném:

try {
  await pool.query("INSERT INTO books (title, author, isbn) VALUES ('Số đỏ', 'Vũ Trọng Phụng', '1')");
  await pool.query("INSERT INTO books (title, author, isbn) VALUES ('Số đỏ', 'Vũ Trọng Phụng', '1')");
} catch (err) {
  console.log(err instanceof pg.DatabaseError);   // true
  console.log(err.code);         // '23505'
  console.log(err.constraint);   // 'books_isbn_key'
  console.log(err.detail);       // 'Key (isbn)=(1) already exists.'
  console.log(err.message);      // 'duplicate key value violates unique constraint "books_isbn_key"'
}

Hai trường quan trọng nhất là code và constraint. code là mã SQLSTATE 5 ký tự, chuẩn chung của SQL, không đổi giữa các phiên bản. constraint là tên ràng buộc bị vi phạm. Đừng dựa vào message: nó là câu cho người đọc, có thể đổi theo phiên bản hoặc theo ngôn ngữ cài trên server.

Để ý hai dòng ghi "lẽ ra phải chặn trước". Zod kiểm tra trước để trả về thông báo lỗi dễ hiểu cho từng trường. Ràng buộc trong database là hàng rào cuối cùng, cho những trường hợp code có lỗi hoặc có ai đó ghi thẳng vào database. Khi hàng rào cuối bị chạm, đó thường là dấu hiệu hai lớp đang không khớp nhau.

ISBN trùng: đừng hỏi trước, cứ ghi rồi bắt lỗi

Kho Map của tuần 1 có lẽ kiểm tra ISBN như thế này:

// Kiểm tra trước rồi mới ghi: có lỗ hổng
const existing = await store.findByIsbn(input.isbn);
if (existing) throw new AppError(409, 'ISBN_TAKEN', 'ISBN này đã có trong kho');
return store.createBook(input);

Với Map trong một tiến trình Node, cách này đúng, vì không có await nào chen giữa lúc kiểm tra và lúc ghi. Với database thì có. Hai request cùng ISBN đến cùng lúc, cả hai cùng thấy "chưa có", cả hai cùng ghi. Không có UNIQUE thì bạn có hai cuốn trùng ISBN. Có UNIQUE thì request thứ hai nhận lỗi 23505, và vì bạn không bắt nó, client thấy lỗi 500.

Cách đúng là bỏ câu hỏi trước, để database quyết định:

// src/db.ts
export function isUniqueViolation(err: unknown, constraint: string): boolean {
  return err instanceof pg.DatabaseError && err.code === '23505' && err.constraint === constraint;
}
// src/book-service.ts
export async function createBook(input: NewBook) {
  try {
    return await store.createBook(input);
  } catch (err) {
    if (isUniqueViolation(err, 'books_isbn_key')) {
      throw new AppError(409, 'ISBN_TAKEN', 'ISBN này đã có trong kho');
    }
    throw err;
  }
}

Hai chi tiết nhỏ mà quan trọng:

  • return await, không phải return. Viết return store.createBook(input) thì hàm trả Promise ra ngoài trước khi nó bị từ chối, và lỗi đi qua catch mà không bị bắt. Đây là bài "lỗi lan thế nào" của tuần 1.
  • Kiểm tra cả tên ràng buộc. Sau này bảng có thêm UNIQUE khác, ví dụ trên một mã nội bộ. Chỉ nhìn 23505 thì bạn sẽ báo "ISBN trùng" cho một lỗi hoàn toàn khác.

Làm y như vậy cho updateBook: PATCH đổi ISBN sang một ISBN đã có cũng phải trả 409.

Id không hợp lệ: chặn trước khi gửi SQL

GET /books/abc đưa chuỗi 'abc' vào WHERE id = $1. PostgreSQL báo 22P02 invalid input syntax for type bigint, và client thấy lỗi 500. Với client, sách abc đơn giản là không tồn tại:

const BookId = z.coerce.number().int().positive();

app.get('/books/:id', async (c) => {
  const id = BookId.safeParse(c.req.param('id'));
  if (!id.success) throw new AppError(404, 'NOT_FOUND', 'Không có sách này');
  const book = await store.getBook(id.data);
  if (!book) throw new AppError(404, 'NOT_FOUND', 'Không có sách này');
  return c.json(book);
});

.int() của zod 4 chỉ nhận số nguyên an toàn, nên một id dài 30 chữ số cũng bị chặn ở đây, thay vì gây lỗi tràn số trong database. Viết test cho cả hai: /books/abc và /books/999999999999999999999999 đều trả 404.

Lỗi không lường trước: 500, và không lộ gì

Lỗi database nào không được chuyển thành AppError sẽ rơi vào nhánh 500 của app.onError từ tuần 1. Giữ nguyên nguyên tắc: ghi log đầy đủ, trả về một thông báo chung chung. Đặc biệt đừng trả err.detail: nó chứa giá trị thật trong dòng bị lỗi, như Key (phone)=(0901234567) already exists. Đó là số điện thoại của người khác.

Database chết thì sao

Thêm một endpoint để biết app có nói chuyện được với database không:

app.get('/health', async (c) => {
  try {
    await pool.query('SELECT 1');
    return c.json({ ok: true });
  } catch (err) {
    console.error('[health]', err);
    return c.json({ ok: false }, 503);
  }
});

Thử: chạy npm run dev, gọi curl -i localhost:3000/health, rồi docker compose stop db và gọi lại. Bạn sẽ thấy 503. Bật lại database bằng npm run db:start, gọi lần nữa: 200, không cần khởi động lại app. Pool tự mở kết nối mới khi database sống lại. Khi deploy ở tuần 8, nền tảng hosting sẽ gọi endpoint này để biết bản app nào còn khoẻ.

Thêm statement_timeout: 5_000 vào cấu hình pool. Một truy vấn chạy quá 5 giây sẽ bị huỷ với mã 57014, thay vì giữ kết nối mãi và làm cạn pool.

Bút đỏ: những câu nghe đúng mà sai

"SELECT xem ISBN có chưa, chưa có thì INSERT. Thế là đủ chặn trùng."Hai request cùng lúc đều thấy chưa có và cùng ghi. Để UNIQUE quyết định, rồi bắt lỗi 23505 theo đúng tên ràng buộc.

"Kiểm tra err.message có chữ duplicate là được."Message là câu cho người đọc và có thể đổi. Dùng err.code và err.constraint.

"Trả nguyên err.detail cho client để dễ debug."detail chứa giá trị thật trong dữ liệu, có thể là thông tin cá nhân của người khác. Ghi vào log, không trả ra ngoài.

"Đã có ràng buộc trong database thì không cần validate bằng zod."Cần cả hai. Zod cho thông báo lỗi theo từng trường mà client hiển thị được. Ràng buộc là lưới an toàn cuối cùng.

Câu hỏi phỏng vấn

Làm sao chặn trùng email hay số điện thoại khi có nhiều request cùng lúc?

Đặt ràng buộc UNIQUE trong database, rồi cứ ghi và bắt lỗi vi phạm, với PostgreSQL là mã 23505 kèm tên ràng buộc. Kiểm tra trước bằng SELECT không đủ, vì giữa lúc kiểm tra và lúc ghi, một request khác có thể đã ghi. Tôi vẫn có thể kiểm tra trước để hiện lỗi sớm trên form, nhưng quyết định cuối cùng thuộc về ràng buộc.

Bạn chuyển lỗi database thành response HTTP thế nào?

Ở lớp service, tôi bắt những lỗi tôi lường trước, dựa vào mã SQLSTATE và tên ràng buộc, rồi đổi thành lỗi nghiệp vụ có mã HTTP rõ ràng: trùng thì 409, tham chiếu tới thứ không tồn tại thì 422. Những lỗi còn lại rơi vào một chỗ xử lý chung, được ghi log đầy đủ và trả về 500 với thông báo chung chung, không lộ chi tiết của database.

Validate ở ứng dụng hay ràng buộc ở database?

Cả hai, mỗi bên một việc. Validate ở ứng dụng để trả lỗi sớm, rõ ràng cho từng trường. Ràng buộc ở database để dữ liệu đúng dù có lỗi trong code, có request chạy đồng thời, hay có người ghi thẳng vào database. Những quy tắc không bao giờ được sai, như số tiền dương hay không trùng, tôi luôn đặt trong database.
