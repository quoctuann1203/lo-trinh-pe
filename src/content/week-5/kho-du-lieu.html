Trong một câu

Lớp store (kho dữ liệu) là một file gom mọi câu SQL của một loại dữ liệu vào các hàm có kiểu rõ ràng, như getBook(id), createBook(input). Route và service chỉ gọi hàm, không viết SQL, và không phải lo đổi kiểu dữ liệu từ database sang JavaScript.

Hình dung thủ kho của quán: đầu bếp chỉ nói "cho tôi 2 kg thịt", thủ kho biết thịt nằm ngăn nào, cân đúng, ghi sổ. Đầu bếp không cần biết kho xếp ra sao.

Vì sao cần một lớp store

Postgres và JavaScript không hiểu kiểu dữ liệu giống nhau: count(*) về JavaScript là chuỗi '42', cột numeric cũng là chuỗi, tên cột viết kiểu created_at thay vì createdAt. Nếu SQL rải khắp các route, mỗi chỗ tự đổi kiểu một cách, sớm muộn sẽ có chỗ quên. Gom về một chỗ thì đổi kiểu đúng một lần, và đổi từ Map sang Postgres chỉ phải viết lại file store.

Làm thử: đoán trước khi chạy

Ghi vào notes kiểu JavaScript mà bạn nghĩ mỗi cột sẽ có, rồi mới chạy trên database books của sql-practice:

const { rows } = await pool.query(`
  SELECT count(*)              AS so_sach,
         sum(price)            AS tong_gia,
         max(id)               AS id_lon_nhat,
         1.5::numeric          AS so_le,
         '2026-12-01'::date    AS ngay,
         now()                 AS luc_nay,
         ARRAY['a', 'b']       AS nhan
  FROM books
`);
for (const [cot, giaTri] of Object.entries(rows[0])) {
  console.log(cot, typeof giaTri, giaTri);
}

Ba dòng đầu gây ra lỗi kinh điển:

const { rows: [{ so_sach }] } = await pool.query('SELECT count(*) AS so_sach FROM books');
console.log(so_sach + 1);      // "41", không phải 5

Dòng ngày tháng còn nguy hiểm hơn, vì nó chỉ sai trên một số máy. Máy bạn ở UTC+7 và in bằng toISOString() thì thấy ngày 30/11. Server deploy ở UTC thì thấy đúng 1/12. Học phí "tháng 12" thành "tháng 11" tuỳ server đặt ở đâu.

Quyết định một lần, ở một chỗ

pg cho phép đổi cách đọc từng kiểu bằng type parser. Đặt nó trong file tạo pool, để mọi truy vấn đều theo cùng một quy tắc:

// src/db.ts
import pg from 'pg';

const { builtins } = pg.types;

// bigint thành number, nhưng báo lỗi nếu số quá lớn thay vì âm thầm làm sai.
// Học phí tính bằng đồng: 9 triệu tỉ đồng mới chạm giới hạn, nên an toàn.
pg.types.setTypeParser(builtins.INT8, (value) => {
  const n = Number(value);
  if (!Number.isSafeInteger(n)) throw new Error(`bigint vượt giới hạn của number: ${value}`);
  return n;
});

// date giữ nguyên chuỗi '2026-12-01'. Không có giờ thì không có múi giờ để lệch.
pg.types.setTypeParser(builtins.DATE, (value) => value);

export const pool = new pg.Pool({ /* như bài trước */ });

Chạy lại bài đoán: so_sach giờ là số 4, ngay là chuỗi '2026-12-01'.

Còn một bẫy. sum() của cột bigint trả về numeric, không phải bigint, nên nó vẫn là chuỗi. Với tiền trong hocphi, ép kiểu ngay trong SQL:

SELECT COALESCE(SUM(amount), 0)::bigint AS paid FROM payments WHERE invoice_id = $1;
-- ::bigint để pg dùng parser INT8 ở trên, ra number

COALESCE(..., 0) cũng cần: hoá đơn chưa có khoản đóng nào thì SUM trả NULL, không phải 0.

Lớp store

Ở tuần 1 bạn đã tách route, service và store. Store là nơi duy nhất biết dữ liệu nằm ở đâu và trông thế nào trong database. Bây giờ nó có thêm việc: đổi một dòng SQL thành object mà phần còn lại của app dùng.

// src/book-store.ts
import { pool } from './db.js';

export type Book = {
  id: number;
  title: string;
  author: string;
  isbn: string;
  publishedYear: number | null;
  tags: string[];
  createdAt: string;
};

type BookRow = {
  id: number;
  title: string;
  author: string;
  isbn: string;
  published_year: number | null;
  tags: string[];
  created_at: Date;
};

const COLUMNS = 'id, title, author, isbn, published_year, tags, created_at';

function toBook(row: BookRow): Book {
  return {
    id: row.id,
    title: row.title,
    author: row.author,
    isbn: row.isbn,
    publishedYear: row.published_year,
    tags: row.tags,
    createdAt: row.created_at.toISOString(),
  };
}

export async function getBook(id: number): Promise<Book | null> {
  const { rows } = await pool.query<BookRow>(`SELECT ${COLUMNS} FROM books WHERE id = $1`, [id]);
  return rows[0] ? toBook(rows[0]) : null;
}

Vài điều đáng để ý:

  • Liệt kê cột thay vì SELECT *. Thứ Bảy tuần trước bạn đã thêm, bỏ cột bằng migration. Với SELECT *, thêm một cột internal_note là nó lọt ra API ngay. Với danh sách cột, bạn phải chủ động thêm.
  • pool.query<BookRow> chỉ là lời hứa với TypeScript. pg không kiểm tra gì cả. Bạn viết sai tên cột thì TypeScript vẫn tin. Đó là lý do lớp store phải có test chạy trên database thật, bài Thứ Năm.
  • Không tìm thấy thì trả null, không ném lỗi 404. Store không biết HTTP. Service hoặc route quyết định null nghĩa là 404.
  • Hàm giờ là async. Kho Map của tuần 1 trả kết quả ngay. Kho PostgreSQL trả Promise, nên mọi chỗ gọi store phải thêm await. TypeScript sẽ chỉ ra những chỗ bạn quên, nếu bạn chạy npm run typecheck.

Thêm và sửa: RETURNING

export async function createBook(input: NewBook): Promise<Book> {
  const { rows } = await pool.query<BookRow>(
    `INSERT INTO books (title, author, isbn, published_year, tags)
     VALUES ($1, $2, $3, $4, $5)
     RETURNING ${COLUMNS}`,
    [input.title, input.author, input.isbn, input.publishedYear ?? null, input.tags],
  );
  return toBook(rows[0]);
}

RETURNING trả về dòng vừa ghi, có cả id và created_at do database sinh. Không cần câu SELECT thứ hai. Để ý ?? null: trường không gửi lên thì ghi rõ là NULL, để người đọc code không phải đoán pg làm gì với undefined.

PATCH chỉ sửa những trường được gửi lên. Tên cột không thể là tham số, nên dùng lại cách danh sách cho phép của bài trước:

const PATCHABLE = {
  title: 'title',
  author: 'author',
  isbn: 'isbn',
  publishedYear: 'published_year',
  tags: 'tags',
} as const;

export async function updateBook(id: number, patch: BookPatch): Promise<Book | null> {
  const fields = (Object.keys(PATCHABLE) as (keyof typeof PATCHABLE)[]).filter(
    (k) => patch[k] !== undefined,
  );
  // Schema zod của tuần 2 đã chặn body rỗng {}, nên fields luôn có ít nhất một phần tử.
  const sets = fields.map((k, i) => `${PATCHABLE[k]} = $${i + 2}`);
  const { rows } = await pool.query<BookRow>(
    `UPDATE books SET ${sets.join(', ')} WHERE id = $1 RETURNING ${COLUMNS}`,
    [id, ...fields.map((k) => patch[k])],
  );
  return rows[0] ? toBook(rows[0]) : null;
}

Chuỗi được ghép vào SQL chỉ có tên cột lấy từ PATCHABLE và các chỗ trống $2, $3. Giá trị vẫn đi qua tham số.

Bút đỏ: những câu nghe đúng mà sai

"count(*) trả về số, cộng thẳng được."count(*) là bigint, pg mặc định trả chuỗi. "4" + 1 là "41". Đặt type parser cho INT8 hoặc ép kiểu trong SQL.

"Cột date đọc ra Date của JavaScript, cứ dùng."pg tạo Date lúc nửa đêm theo múi giờ của máy chạy Node, nên cùng một dòng cho ra ngày khác nhau trên máy khác nhau. Giữ date dạng chuỗi YYYY-MM-DD.

"Đã ghi pool.query<BookRow> thì kiểu chắc chắn đúng."Đó chỉ là lời hứa với TypeScript, không ai kiểm tra lúc chạy. Test trên database thật mới bắt được tên cột sai.

Tự kiểm tra

Tự trả lời trước, rồi mới bấm mở đáp án.

SELECT count(*) FROM books qua pg trả về { count: '42' }. Vì sao là chuỗi, xử lý ở đâu?

count là bigint, pg trả chuỗi để khỏi mất chính xác. Đổi sang số trong lớp store, một lần cho mọi nơi.

Route có nên viết SQL trực tiếp không?

Không: route lo HTTP, store lo database. Route gọi hàm của store.

Thêm sách xong cần trả về sách vừa tạo kèm id. Có cần SELECT lại không?

Không, dùng INSERT ... RETURNING *.

Câu hỏi phỏng vấn

Vì sao node-postgres trả bigint về dạng chuỗi?

Vì number của JavaScript chỉ biểu diễn chính xác số nguyên tới khoảng 9 triệu tỉ, còn bigint của PostgreSQL lớn hơn nhiều. Nếu tự đổi sang number, giá trị lớn sẽ bị làm tròn mà không ai biết. Thư viện chọn cách an toàn là trả chuỗi và để ứng dụng quyết định. Trong dự án học phí, tôi đổi bigint sang number ở một chỗ duy nhất, kèm kiểm tra Number.isSafeInteger để báo lỗi nếu có giá trị vượt giới hạn.

Repository hay lớp store dùng để làm gì?

Nó gom mọi chi tiết về lưu trữ vào một chỗ: câu SQL, tên cột snake_case, cách đổi kiểu. Phần nghiệp vụ chỉ làm việc với object có kiểu rõ ràng và không biết dữ liệu nằm ở PostgreSQL hay ở đâu. Nhờ vậy đổi cách lưu không đụng tới quy tắc nghiệp vụ, và quy tắc nghiệp vụ test được mà không cần database.

Vì sao bạn không dùng SELECT * trong code ứng dụng?

Vì kết quả của nó thay đổi mỗi khi schema thay đổi. Một cột mới, có thể là dữ liệu nội bộ, sẽ tự lọt ra API. Thứ tự và tên cột cũng không còn được ghi rõ trong code. Liệt kê cột giúp tôi thấy chính xác truy vấn trả về gì, và đọc ít dữ liệu hơn khi bảng có cột lớn.

Nhớ 3 ý

  1. Mọi SQL của một loại dữ liệu nằm trong lớp store, sau các hàm có kiểu rõ.
  2. Đổi kiểu từ database sang JavaScript (chuỗi số, tên cột) đúng một lần, ở store.
  3. Dùng RETURNING để lấy dòng vừa ghi; không tìm thấy thì trả null.
