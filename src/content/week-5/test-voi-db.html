Bước 0: books-api có database riêng

API sách là một repo riêng, nên nó có Postgres riêng, giống cách bạn làm cho hocphi ở tuần 4. Cổng ngoài là 5434, để chạy song song được với sql-practice (5432) và hocphi (5433). Thêm compose.yaml ở gốc books-api:

services:
  db:
    image: postgres:18
    environment:
      POSTGRES_USER: books
      POSTGRES_PASSWORD: books        # chỉ dùng trên máy mình
      POSTGRES_DB: books
    ports:
      - "5434:5432"
    volumes:
      - pgdata:/var/lib/postgresql
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U books -d books"]
      interval: 2s
      retries: 15

  dbmate:
    image: ghcr.io/amacneil/dbmate:2.38.2
    profiles: [tools]
    environment:
      DATABASE_URL: postgres://books:books@db:5432/books?sslmode=disable
    volumes:
      - ./db:/db
    depends_on:
      db:
        condition: service_healthy

volumes:
  pgdata:

Migration đầu tiên khớp với schema zod của tuần 1. Trường nào zod cho phép thiếu thì cột đó được NULL. Trường nào zod bắt buộc thì cột đó NOT NULL. Hai nơi phải nói cùng một điều.

-- db/migrations/20261210090000_create_books.sql
-- migrate:up
CREATE TABLE books (
  id             bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  title          text NOT NULL CHECK (length(trim(title)) > 0),
  author         text NOT NULL,
  isbn           text NOT NULL,
  published_year integer CHECK (published_year BETWEEN 1450 AND 2100),
  tags           text[] NOT NULL DEFAULT '{}',
  created_at     timestamptz NOT NULL DEFAULT now(),
  CONSTRAINT books_isbn_key UNIQUE (isbn)
);

-- migrate:down
DROP TABLE books;

Ràng buộc UNIQUE được đặt tên rõ ràng, books_isbn_key. Bài sau, code sẽ dựa vào cái tên đó để biết lỗi nào là "ISBN trùng". Nếu tuần 1 bạn sinh id bằng crypto.randomUUID(), id giờ là số do database sinh. Test tuần 2 tạo sách qua API rồi dùng id trả về, nên chúng không phụ thuộc kiểu id.

Thêm DATABASE_URL=postgres://books:books@localhost:5434/books vào .env, thêm --env-file=.env vào script dev, rồi chạy npm run db:start và npm run db:migrate. Sau đó viết lại book-store.ts theo bài lớp store của Thứ Ba.

Vì sao không giữ kho trong bộ nhớ cho test

Kho Map của tuần 1 chạy rất nhanh, nhưng nó không có những thứ bạn đang dựa vào. Nó không có UNIQUE, nên test "ISBN trùng trả 409" chỉ kiểm tra được đoạn code tự kiểm tra của bạn. Nó không có CHECK, không có khoá ngoại, không có transaction. Và nó không bắt được một tên cột viết sai trong SQL, vì với nó chẳng có SQL nào.

Code càng dựa vào database để giữ dữ liệu đúng, test càng phải chạy trên database thật. Với API sách, gần như mọi thứ đều đi qua database, nên toàn bộ bộ test chạy trên PostgreSQL.

Database test riêng, dựng lại từ migration

Đừng chạy test trên database books bạn đang dùng để phát triển. Có ba lý do:

  1. Test xoá dữ liệu trước mỗi lần chạy. Dữ liệu bạn đang thử tay sẽ mất.
  2. Database dev đã đi qua những lệnh bạn gõ tay trong psql. Test xanh trên đó không chứng minh được gì về migration.
  3. Bạn sửa một migration nhưng quên chạy lại trên database dev, test vẫn chạy trên schema cũ. Đây chính là chuyện trong video: xoá một ràng buộc mà test vẫn xanh.

Cách làm: database books_test riêng, xoá và dựng lại từ migration mỗi lần chạy test. Giống script db:check của tuần 4:

#!/usr/bin/env bash
# scripts/db-test-prepare.sh
set -euo pipefail

TEST_URL='postgres://books:books@db:5432/books_test?sslmode=disable'
dm() { docker compose run --rm -T -e DATABASE_URL="$TEST_URL" dbmate --no-dump-schema "$@"; }

docker compose up -d --wait db
dm drop
dm up

--no-dump-schema để dbmate không ghi đè db/schema.sql bằng bản của database test.

Dọn dữ liệu trước mỗi test

Ở tuần 2, beforeEach(() => resetStore()) xoá kho trong bộ nhớ. Bây giờ nó xoá bảng:

// src/test-helpers.ts
import { pool } from './db.js';

export async function resetDb() {
  await pool.query('TRUNCATE books RESTART IDENTITY CASCADE');
}
// src/books.test.ts
beforeEach(() => resetDb());

TRUNCATE nhanh hơn DELETE vì nó không xoá từng dòng. RESTART IDENTITY đưa bộ đếm id về 1, để id không phụ thuộc vào thứ tự chạy test. CASCADE xoá luôn các bảng trỏ tới books, khi sau này có thêm bảng con.

Có một cách khác hay được nhắc: mở transaction trước mỗi test, rollback sau test. Cách đó chỉ chạy được khi test và code dùng chung đúng một kết nối. Code của bạn mượn kết nối từ pool, mỗi câu có thể đi một kết nối khác. Hôm Thứ Bảy, code còn tự mở transaction riêng. Vì vậy dùng TRUNCATE: đơn giản, và chỉ tốn vài mili-giây với bảng nhỏ.

Chạy, rồi cố tình làm hỏng

npm test

Lần đầu bạn sẽ thấy dbmate in ra vài dòng, rồi test chạy. Test nào đỏ thì thường do một trong ba lý do:

  • Thiếu await ở chỗ gọi store, nên handler trả về một Promise thay vì dữ liệu.
  • Kiểu dữ liệu: test mong publishedYear: 1941 nhưng nhận "1941", hoặc mong id là chuỗi.
  • Thứ tự: GET /books không có ORDER BY thì PostgreSQL trả theo thứ tự nào cũng được. Kho Map luôn giữ thứ tự chèn, còn database thì không hứa điều đó. Thêm ORDER BY id.

Khi đã xanh hết, làm bài kiểm tra chính bộ test. Xoá dòng CONSTRAINT books_isbn_key UNIQUE (isbn) khỏi migration, đừng chạy db:migrate, và chạy npm test. Test "ISBN trùng → 409" phải đỏ, vì database test được dựng lại từ migration đã sửa. Database dev thì vẫn còn UNIQUE. Nếu test chạy trên database dev, nó vẫn xanh và bạn không biết mình vừa làm hỏng gì. Trả dòng đó lại.

Lần đầu sẽ chậm hơn vài chục giây vì phải tải image postgres và dbmate. Push lên và xem dấu xanh.

Bút đỏ: những câu nghe đúng mà sai

"Chạy test trên database dev cho nhanh, khỏi dựng gì thêm."Test sẽ xoá dữ liệu bạn đang dùng, và xanh trên một schema có thể khác hẳn migration. Dùng database test riêng, dựng lại từ migration.

"Mock pool.query để test store cho nhanh."Test đó chỉ kiểm tra rằng bạn gọi đúng chuỗi SQL bạn vừa viết. Nó không bắt được SQL sai, tên cột sai hay ràng buộc thiếu. Store phải được test trên database thật.

"Không có ORDER BY thì database trả theo thứ tự chèn."Không có gì đảm bảo điều đó. Sau khi sửa hay xoá dòng, thứ tự có thể đổi. Muốn thứ tự nào thì viết ORDER BY.

Câu hỏi phỏng vấn

Bạn test code đọc ghi database thế nào?

Tôi chạy integration test trên PostgreSQL thật, trong một database test riêng được xoá và dựng lại từ migration mỗi lần chạy test. Nhờ vậy test kiểm tra cả migration lẫn các ràng buộc như UNIQUE. Trước mỗi test tôi TRUNCATE các bảng, và các file test chạy lần lượt để không xoá dữ liệu của nhau. Logic thuần như tính học phí thì vẫn có unit test riêng, không cần database.

Vì sao không mock database trong test?

Vì phần dễ sai nhất chính là chỗ nói chuyện với database: câu SQL, tên cột, kiểu dữ liệu trả về, ràng buộc. Mock thay đúng phần đó bằng thứ tôi tự viết, nên test chỉ xác nhận lại giả định của tôi. Mock hợp với những thứ chậm hoặc nằm ngoài tầm kiểm soát, như API thanh toán bên thứ ba. Database thì chạy được trên máy và trong CI bằng Docker, nên tôi dùng bản thật.

Làm sao để test dùng database không ảnh hưởng nhau?

Mỗi test bắt đầu từ trạng thái sạch: tôi TRUNCATE bảng với RESTART IDENTITY trong beforeEach, và mỗi test tự tạo dữ liệu nó cần. Các file test chạy tuần tự vì chúng dùng chung database. Nếu bộ test lớn và chậm, có thể cho mỗi worker một database riêng để chạy song song lại.
