Trong một câu

Bài này là bài tổng hợp của tuần 5: cho ứng dụng Next.js hocphi đọc ghi database thật. Bạn làm API danh sách hoá đơn trong tháng, chức năng ghi khoản đóng an toàn khi nhiều người cùng ghi, và bộ test chứng minh nó đúng.

Hình dung lắp điện cho căn nhà đã xây xong ở tuần 4: đi dây (kết nối), lắp công tắc (các hàm đọc ghi), rồi bật thử từng phòng (test), kể cả bật hai công tắc cùng lúc.

Vì sao làm bài tổng hợp này

Mỗi bài trước dạy một mảnh: pool, tham số, store, lỗi database, transaction, khoá dòng, test. Ghép vào một sản phẩm thật mới lộ ra chỗ các mảnh chạm nhau, ví dụ transaction phải chạy cùng kết nối với hàm store, hay test cùng lúc 10 request mới thấy lỗi đồng thời.

Từ khoá cần biết

server-only
Gói đánh dấu file chỉ được chạy trên server, để code database không lọt vào trình duyệt.
.env.local
File biến môi trường của Next.js trên máy bạn, không commit.
Route Handler
File route.ts trong src/app/api/..., export hàm GET, POST… để Next.js trả lời request API. Bài này viết API của hocphi bằng cách đó.
Pool dùng chung
Một pool cho cả app Next.js, giữ qua các lần tải lại code khi dev.

Làm thử, bước 1: hocphi nói chuyện với database

Từ tuần 4, database của hocphi chạy ở cổng 5433 và schema nằm trong db/migrations. Giờ đến lượt code Next.js đọc ghi nó.

npm install pg server-only
npm install -D @types/pg
# .env.local, không commit
DATABASE_URL=postgres://hocphi:hocphi@localhost:5433/hocphi
DEV_TEACHER_ID=1

Thêm hai tên biến này, không có giá trị, vào .env.example. Next.js tự đọc .env.local khi chạy next dev. Biến không có tiền tố NEXT_PUBLIC_ chỉ tồn tại trên server, nên mật khẩu database không bao giờ bị đưa xuống trình duyệt.

DEV_TEACHER_ID là chỗ tạm, cho tới khi có đăng nhập ở tuần 6. Mọi truy vấn từ hôm nay đã lọc theo giáo viên. Tuần sau bạn chỉ đổi chỗ lấy con số đó, không phải sửa câu SQL nào:

// src/lib/auth.ts
import 'server-only';

/** Tạm thời: tuần 6 thay bằng giáo viên lấy từ session đăng nhập. */
export function currentTeacherId(): number {
  const id = Number(process.env.DEV_TEACHER_ID);
  if (!Number.isSafeInteger(id) || id <= 0) throw new Error('Thiếu DEV_TEACHER_ID trong .env.local');
  return id;
}

Bước 2: một pool cho cả app

// src/lib/db/pool.ts
import 'server-only';
import pg from 'pg';

const { builtins } = pg.types;
pg.types.setTypeParser(builtins.INT8, (value) => {
  const n = Number(value);
  if (!Number.isSafeInteger(n)) throw new Error(`bigint vượt giới hạn của number: ${value}`);
  return n;
});
pg.types.setTypeParser(builtins.DATE, (value) => value);

function createPool() {
  const pool = new pg.Pool({
    connectionString: process.env.DATABASE_URL,
    max: 10,
    connectionTimeoutMillis: 5_000,
    statement_timeout: 5_000,
  });
  pool.on('error', (err) => console.error('[pg pool]', err));
  return pool;
}

Bước 3: danh sách hoá đơn trong tháng

Đây là câu hỏi 1 của tuần 3, giờ thành API. Store trước:

// src/lib/db/invoices.ts
import 'server-only';
import type { Db } from './tx';

export type InvoiceSummary = {
  id: number;
  className: string;
  studentName: string;
  billingMonth: string;
  amount: number;
  paid: number;
  remaining: number;
};

export async function listInvoices(db: Db, teacherId: number, month: string): Promise<InvoiceSummary[]> {
  const { rows } = await db.query<{
    id: number; class_name: string; student_name: string;
    billing_month: string; amount: number; paid: number;
  }>(
    `SELECT i.id, c.name AS class_name, s.name AS student_name,
            i.billing_month, i.amount,
            COALESCE(SUM(p.amount), 0)::bigint AS paid
     FROM invoices i
     JOIN classes  c ON c.id = i.class_id
     JOIN students s ON s.id = i.student_id
     LEFT JOIN payments p ON p.invoice_id = i.id
     WHERE c.teacher_id = $1 AND i.billing_month = $2
     GROUP BY i.id, c.name, s.name
     ORDER BY c.name, s.name`,
    [teacherId, month],
  );
  return rows.map((r) => ({
    id: r.id,
    className: r.class_name,
    studentName: r.student_name,
    billingMonth: r.billing_month,
    amount: r.amount,
    paid: r.paid,
    remaining: r.amount - r.paid,
  }));
}

Dòng WHERE c.teacher_id = $1 quan trọng không kém câu SQL còn lại. Thiếu nó, giáo viên này thấy hoá đơn của mọi giáo viên khác. Đó là lỗi 403 hay 404 bạn đã viết test ở tuần 2, giờ nằm trong SQL.

// src/app/api/invoices/route.ts
import type { NextRequest } from 'next/server';
import { z } from 'zod';
import { currentTeacherId } from '@/lib/auth';
import { pool } from '@/lib/db/pool';
import { listInvoices } from '@/lib/db/invoices';
import { problem } from '@/lib/http';

const Query = z.object({
  month: z.iso.date().refine((d) => d.endsWith('-01'), 'Tháng phải là ngày mùng 1, ví dụ 2026-12-01'),
});

export async function GET(request: NextRequest) {
  const query = Query.safeParse(Object.fromEntries(request.nextUrl.searchParams));
  if (!query.success) {
    return problem(422, 'VALIDATION', 'Tham số không hợp lệ', { details: z.flattenError(query.error) });
  }
  const invoices = await listInvoices(pool, currentTeacherId(), query.data.month);
  return Response.json({ invoices });
}
// src/lib/http.ts: cùng định dạng lỗi với API sách tuần 1
export function problem(status: number, code: string, message: string, extra: Record<string, unknown> = {}) {
  return Response.json({ error: { code, message, ...extra } }, { status });
}

Bước 4: ghi khoản đóng

Ghép mọi thứ của tuần này lại: tham số, transaction, khoá dòng, kiểm tra quyền, và bắt lỗi theo mã.

// src/lib/db/payments.ts
import 'server-only';
import { withTransaction } from './tx';

export type Payment = { id: number; invoiceId: number; amount: number; paidAt: string };

export type RecordPaymentResult =
  | { kind: 'ok'; payment: Payment; remaining: number }
  | { kind: 'not_found' }
  | { kind: 'overpaid'; remaining: number };

export async function recordPayment(input: {
  teacherId: number;
  invoiceId: number;
  amount: number;
}): Promise<RecordPaymentResult> {
  return withTransaction(async (tx) => {
    await tx.query("SET LOCAL lock_timeout = '3s'");

    // 1. Khoá hoá đơn, đồng thời kiểm tra nó thuộc về giáo viên này
    const invoice = await tx.query<{ amount: number }>(
      `SELECT i.amount
       FROM invoices i
       JOIN classes c ON c.id = i.class_id
       WHERE i.id = $1 AND c.teacher_id = $2
       FOR UPDATE OF i`,
      [input.invoiceId, input.teacherId],
    );
    if (invoice.rowCount === 0) return { kind: 'not_found' };

    // 2. Đọc tổng đã đóng. Có khoá rồi nên không ai chen vào giữa bước 2 và bước 3
    const { rows: [{ paid }] } = await tx.query<{ paid: number }>(
      'SELECT COALESCE(SUM(amount), 0)::bigint AS paid FROM payments WHERE invoice_id = $1',
      [input.invoiceId],
    );
    const remaining = invoice.rows[0].amount - paid;
    if (input.amount > remaining) return { kind: 'overpaid', remaining };

    // 3. Ghi
    const { rows: [row] } = await tx.query<{ id: number; invoice_id: number; amount: number; paid_at: Date }>(
      `INSERT INTO payments (invoice_id, amount)
       VALUES ($1, $2)
       RETURNING id, invoice_id, amount, paid_at`,
      [input.invoiceId, input.amount],
    );
    return {
      kind: 'ok',
      payment: { id: row.id, invoiceId: row.invoice_id, amount: row.amount, paidAt: row.paid_at.toISOString() },
      remaining: remaining - input.amount,
    };
  });
}

Vài điểm đáng nói khi thu âm hôm Chủ nhật:

  • FOR UPDATE OF i: câu có JOIN, và FOR UPDATE trơn sẽ khoá cả dòng lớp học. Mọi khoản đóng của cả lớp sẽ phải xếp hàng chờ nhau. OF i chỉ khoá dòng hoá đơn.
  • Hoá đơn của giáo viên khác trả not_found, giống hệt hoá đơn không tồn tại. Trả 403 sẽ cho người lạ biết hoá đơn đó có thật.
  • Hàm trả về kết quả có kiểu thay vì ném lỗi HTTP. Store không biết HTTP. TypeScript bắt route xử lý đủ ba trường hợp.
  • return bên trong callback vẫn đi qua COMMIT. Với not_found và overpaid, chưa có gì được ghi, nên commit cũng như rollback.
// src/app/api/invoices/[id]/payments/route.ts
import pg from 'pg';
import { z } from 'zod';
import { currentTeacherId } from '@/lib/auth';
import { recordPayment } from '@/lib/db/payments';
import { problem } from '@/lib/http';

const InvoiceId = z.coerce.number().int().positive();
const Body = z.strictObject({ amount: z.number().int().positive() });

export async function POST(request: Request, ctx: RouteContext<'/api/invoices/[id]/payments'>) {
  const id = InvoiceId.safeParse((await ctx.params).id);
  if (!id.success) return problem(404, 'NOT_FOUND', 'Không có hoá đơn này');

  let json: unknown;
  try {
    json = await request.json();
  } catch {
    return problem(400, 'INVALID_JSON', 'Body không phải JSON hợp lệ');
  }
  const body = Body.safeParse(json);
  if (!body.success) {
    return problem(422, 'VALIDATION', 'Dữ liệu không hợp lệ', { details: z.flattenError(body.error) });
  }

  try {
    const result = await recordPayment({ teacherId: currentTeacherId(), invoiceId: id.data, amount: body.data.amount });
    switch (result.kind) {
      case 'ok':
        return Response.json({ payment: result.payment, remaining: result.remaining }, { status: 201 });
      case 'not_found':
        return problem(404, 'NOT_FOUND', 'Không có hoá đơn này');
      case 'overpaid':
        return problem(409, 'OVERPAYMENT', 'Số tiền lớn hơn số còn thiếu', { remaining: result.remaining });
    }
  } catch (err) {
    if (err instanceof pg.DatabaseError && err.code === '55P03') {
      return problem(409, 'INVOICE_BUSY', 'Hoá đơn đang được cập nhật, thử lại sau ít giây');
    }
    throw err;
  }
}

RouteContext là kiểu toàn cục do Next.js sinh ra khi chạy next dev, next build hoặc next typegen. Nếu TypeScript báo không tìm thấy nó, chạy npx next typegen. Thử bằng curl: đóng 100.000, đóng số lớn hơn số còn thiếu, đóng vào hoá đơn của giáo viên số 2.

  const invoice = await q(
    "INSERT INTO invoices (class_id, student_id, billing_month, amount) VALUES ($1, $2, '2026-12-01', $3) RETURNING id",

  );
  return { teacherId: teacher.id as number, invoiceId: invoice.id as number };

Bước 7: bấm hai lần không thành hai khoản đóng

Khoá dòng không giúp được khi cùng một request bị gửi hai lần: mạng chậm, giáo viên bấm lại, trình duyệt tự gửi lại. Cách làm của các dịch vụ thanh toán: client sinh một mã ngẫu nhiên cho mỗi lần đóng tiền và gửi kèm trong header Idempotency-Key. Server ghi mã đó cùng khoản đóng. Gặp lại mã cũ thì trả lại khoản đóng cũ thay vì ghi mới.

npm run db:new -- add_payments_request_id
-- db/migrations/20261212150000_add_payments_request_id.sql
-- migrate:up
ALTER TABLE payments ADD COLUMN request_id uuid;
ALTER TABLE payments ADD CONSTRAINT payments_request_id_key UNIQUE (request_id);

-- migrate:down
ALTER TABLE payments DROP COLUMN request_id;

Cột được phép NULL, vì các khoản đóng cũ không có mã, và UNIQUE cho phép nhiều NULL. Bảng nhỏ nên thêm UNIQUE trực tiếp là được. Với bảng hàng triệu dòng, bạn sẽ tạo index CONCURRENTLY trước, như tuần 4. Chạy npm run db:migrate và npm run db:check.

Trong recordPayment, nhận thêm requestId, và thêm hai trường hợp { kind: 'replay'; payment: Payment } và { kind: 'key_reused' } vào RecordPaymentResult. Thêm hai nhánh tương ứng vào switch trong route. Để TypeScript nhắc bạn khi quên, thêm default: return result satisfies never; làm nhánh cuối. Ngay sau khi khoá hoá đơn, trước khi tính tổng, tìm xem mã đó đã được dùng chưa:

const existing = await tx.query<{ id: number; invoice_id: number; amount: number; paid_at: Date }>(
  'SELECT id, invoice_id, amount, paid_at FROM payments WHERE request_id = $1',
  [input.requestId],
);
if (existing.rows[0]) {
  const row = existing.rows[0];
  if (row.invoice_id !== input.invoiceId) return { kind: 'key_reused' };
  return { kind: 'replay', payment: { id: row.id, invoiceId: row.invoice_id, amount: row.amount, paidAt: row.paid_at.toISOString() } };
}
// ... phần tính tổng giữ nguyên, rồi INSERT thêm cột request_id = $3

Thứ tự ở đây quan trọng. Kiểm tra mã phải đứng sau FOR UPDATE. Hai request cùng mã tới cùng lúc thì request thứ hai chờ ở khoá, rồi mới thấy mã đã có. Nếu kiểm tra mã trước khi khoá, cả hai cùng thấy "chưa có". Khi đó UNIQUE chặn lần ghi thứ hai với lỗi 23505, và client nhận lỗi thay vì khoản đóng cũ. Vẫn bắt lỗi đó trong route và trả 409 DUPLICATE_REQUEST, phòng khi hai request cùng mã đi vào hai hoá đơn khác nhau.

Trong route, đọc header trước khi đọc body:

const key = z.uuid().safeParse(request.headers.get('Idempotency-Key'));
if (!key.success) return problem(400, 'IDEMPOTENCY_KEY_REQUIRED', 'Cần header Idempotency-Key dạng UUID');

Ở phía giao diện, mã được sinh một lần khi mở form đóng tiền, không phải mỗi lần bấm nút. Bấm lại sau lỗi mạng dùng lại mã cũ. Tuần 11 làm form bạn sẽ nối phần này.

Bút đỏ: những câu nghe đúng mà sai

"Chưa có đăng nhập thì chưa cần lọc theo giáo viên."Thêm teacher_id vào SQL từ đầu, lấy tạm từ biến môi trường. Thêm sau thì sẽ có một câu SQL bị quên.

"Disable nút sau khi bấm là đủ chống bấm hai lần."Nút disable không chặn được việc mạng gửi lại, tab thứ hai, hay app khác gọi API. Server phải tự nhận ra request trùng bằng idempotency key.

"Hoá đơn của giáo viên khác thì trả 403 cho đúng nghĩa."403 cho người lạ biết hoá đơn đó tồn tại. Với dữ liệu của người khác, trả 404 như thể nó không có.

"Mỗi lần lưu file, next dev tạo pool mới cũng không sao."Pool cũ vẫn giữ kết nối. Sau vài chục lần lưu, Postgres báo too many clients. Giữ pool trên globalThis khi chạy dev.

Tự kiểm tra

Tự trả lời trước, rồi mới bấm mở đáp án.

Vì sao file tạo pool cần import 'server-only'?

Để nếu lỡ import nó từ component chạy ở trình duyệt thì build báo lỗi, thay vì đưa chuỗi kết nối database ra trình duyệt.

Test gửi 10 request ghi khoản đóng cùng lúc để kiểm tra điều gì?

Rằng tổng nhận không vượt số tiền hoá đơn khi nhiều request chen nhau, tức khoá dòng hoạt động đúng.

Bấm nút ghi khoản đóng hai lần, vì sao không được thành hai khoản?

Vì đó là cùng một lần đóng tiền; mã chống bấm hai lần giúp server nhận ra và trả lại kết quả lần đầu.

Câu hỏi phỏng vấn

Kể cách bạn làm một endpoint ghi nhận thanh toán.

Endpoint nhận id hoá đơn, số tiền và header Idempotency-Key. Sau khi validate, mọi thứ chạy trong một transaction: khoá dòng hoá đơn bằng SELECT FOR UPDATE, đồng thời kiểm tra hoá đơn thuộc về giáo viên đang đăng nhập; kiểm tra mã idempotency đã được dùng chưa; tính số còn thiếu; nếu số tiền không vượt quá thì ghi. Có ba lớp bảo vệ: khoá dòng chặn hai người ghi cùng lúc, idempotency key chặn một request bị gửi hai lần, và ràng buộc UNIQUE trên mã là lưới an toàn cuối cùng. Tôi có test gửi 10 request cùng lúc, và đã thấy test đó đỏ khi bỏ khoá.

Idempotency là gì? Vì sao API thanh toán cần nó?

Một thao tác idempotent cho cùng kết quả dù được gọi một lần hay nhiều lần. POST tạo thanh toán vốn không như vậy: gửi hai lần là hai khoản. Nhưng client luôn có lý do để gửi lại, như hết thời gian chờ mà không biết server đã ghi hay chưa. Client gửi kèm một mã duy nhất cho mỗi ý định thanh toán. Server lưu mã đó, nếu gặp lại thì trả về kết quả cũ thay vì ghi mới. Nhờ vậy client có thể thử lại an toàn.

Một người dùng có xem được dữ liệu của người khác không? Bạn chặn ở đâu?

Tôi chặn ngay trong câu truy vấn: mọi câu đọc ghi hoá đơn đều nối tới lớp học và lọc theo teacher_id của người đang đăng nhập. Hoá đơn của người khác vì vậy giống hệt hoá đơn không tồn tại, và tôi trả 404 để không lộ là nó có thật. Tôi có test tạo hai giáo viên và kiểm tra giáo viên này không ghi được vào hoá đơn của giáo viên kia.

Nhớ 3 ý

  1. hocphi nối Postgres qua một pool dùng chung, đánh dấu server-only, chuỗi kết nối trong .env.local.
  2. Ghi khoản đóng trong transaction có khoá dòng; bấm hai lần không thành hai khoản.
  3. Test trên database test riêng, kể cả 10 request cùng lúc.
