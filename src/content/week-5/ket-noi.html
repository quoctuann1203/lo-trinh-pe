Trong một câu

Để code Node nói chuyện được với PostgreSQL, bạn cần một driver (thư viện pg) và một pool: một nhóm kết nối mở sẵn, request nào cần thì mượn một kết nối, chạy SQL xong thì trả lại.

Hình dung xe đạp công cộng ở trạm. Mua xe mới cho mỗi chuyến đi thì đắt và chậm; trạm có sẵn 10 chiếc, ai cần thì mượn, đi xong trả lại cho người sau. Pool là trạm xe đó, kết nối là chiếc xe.

Vì sao không mở một kết nối mới cho mỗi request

Mỗi kết nối tới Postgres phải bắt tay qua mạng, xác thực, và Postgres tạo hẳn một tiến trình riêng cho nó. Việc đó tốn vài mili-giây và vài MB bộ nhớ mỗi lần. Mở mới cho từng request thì API chậm hẳn, và lúc đông người, Postgres hết chỗ nhận kết nối. Pool mở sẵn vài kết nối và dùng lại, nên nhanh và giới hạn được số kết nối.

Từ khoá cần biết

Driver
Thư viện nói giao thức riêng của Postgres thay bạn. Với Node là pg (node-postgres).
Kết nối (connection)
Một đường liên lạc đang mở giữa app và Postgres.
Pool
Nhóm kết nối mở sẵn để dùng lại.
pool.query
Mượn một kết nối, chạy một câu SQL, tự trả lại. Dùng cho hầu hết trường hợp.
pool.connect
Mượn một kết nối để chạy nhiều câu trên cùng kết nối (cần cho transaction); phải tự release().
Chuỗi kết nối
URL chứa địa chỉ, cổng, tên database, tài khoản, ví dụ postgres://user:pass@localhost:5432/db.
max
Số kết nối tối đa pool được mở.

Pool hoạt động thế nào

  1. App khởi động, tạo một pool duy nhất từ chuỗi kết nối. Chưa mở kết nối nào.
  2. Request cần SQL gọi pool.query. Pool đưa một kết nối đang rảnh, hoặc mở mới nếu chưa tới max.
  3. Đủ max kết nối đều bận thì request xếp hàng chờ.
  4. Chạy xong, kết nối được trả về pool cho request sau dùng lại.

Driver là gì

PostgreSQL không nói HTTP. Nó có giao thức riêng chạy trên TCP: bắt tay, xác thực, gửi câu lệnh, nhận từng dòng kết quả. Driver là thư viện nói giao thức đó thay bạn. Với Node, driver phổ biến nhất là pg, còn gọi là node-postgres. Các ORM như Drizzle hay Prisma rốt cuộc cũng đi qua một driver như vậy.

npm install pg
npm install -D @types/pg

Một kết nối tốn bao nhiêu

Mỗi lần mở kết nối, Postgres tạo hẳn một tiến trình mới trên server, kiểm tra mật khẩu, cấp vài MB bộ nhớ. Trên máy bạn việc này mất vài mili-giây, qua mạng thật thì lâu hơn. Số kết nối cũng có giới hạn:

SHOW max_connections;      -- 100, giá trị mặc định

Nếu mỗi request mở một kết nối mới rồi đóng, bạn trả chi phí đó cho từng request. Lúc đông người, bạn chạm giới hạn 100 và request thứ 101 bị từ chối.

Pool: mượn rồi trả

Pool mở sẵn một số kết nối và giữ chúng lại. Khi cần chạy truy vấn, code mượn một kết nối rảnh, dùng xong thì trả về. Nếu cả pool đang bận, request mới xếp hàng chờ thay vì mở thêm.

// src/db.ts
import pg from 'pg';

export const pool = new pg.Pool({
  connectionString: process.env.DATABASE_URL,
  max: 10,                        // tối đa 10 kết nối mở cùng lúc
  idleTimeoutMillis: 30_000,      // kết nối rảnh quá 30 giây thì đóng bớt
  connectionTimeoutMillis: 5_000, // chờ mượn quá 5 giây thì báo lỗi, đừng treo mãi
});

// Kết nối đang rảnh trong pool cũng có thể bị đứt, ví dụ khi database khởi động lại.
// Không lắng nghe sự kiện này thì lỗi đó làm sập cả tiến trình Node.
pool.on('error', (err) => console.error('[pg pool]', err));

Mặc định connectionTimeoutMillis là 0, tức là chờ mãi. Khi database chết hay pool cạn, request của bạn treo không có hồi kết thay vì báo lỗi. Luôn đặt một con số.

pool.query và pool.connect

Cách gọiLàm gìDùng khi
pool.query(sql, values)Mượn một kết nối, chạy một câu, tự trả lạiGần như mọi lúc
const client = await pool.connect()Mượn một kết nối và giữ nó cho tới khi bạn gọi client.release()Nhiều câu phải chạy trên cùng một kết nối, như transaction ở Thứ Bảy
 
const { rows, rowCount } = await pool.query('SELECT id, title FROM books WHERE id = $1', [id]);
// rows: mảng object, mỗi object là một dòng. rowCount: số dòng trả về hoặc bị ảnh hưởng.

Quên gọi client.release() là lỗi rò kết nối. Lần đầu chẳng thấy gì. Sau 10 lần, pool hết kết nối để cho mượn và mọi request treo cho tới khi hết connectionTimeoutMillis. Vì vậy release() luôn nằm trong finally.

Chuỗi kết nối và file .env

postgres://người_dùng:mật_khẩu@máy:cổng/tên_database
postgres://hoc:hoc@localhost:5432/books

Chuỗi này có mật khẩu, nên nó nằm trong file .env không commit, còn .env.example chỉ ghi tên biến. Node từ bản 20.6 tự đọc được file .env qua cờ --env-file, không cần gói dotenv:

node --env-file=.env dist/index.js
npx tsx --env-file=.env scripts/thu-pg.ts

Kiểm tra biến môi trường ngay lúc khởi động bằng zod như tuần 1. Thiếu DATABASE_URL thì app phải chết ngay với một thông báo rõ ràng, chứ không phải chạy được rồi mới báo lỗi ở request đầu tiên.

Làm thử: kết nối mới hay pool

Trong thư mục sql-practice của tuần 3, tạo một project Node nhỏ cạnh compose.yaml:

npm init -y
npm install pg
npm install -D tsx @types/pg
echo 'DATABASE_URL=postgres://hoc:hoc@localhost:5432/books' > .env

Đây là database books mà dbmate tạo ở tuần 4, có sẵn bảng authors, books, reviews. Thêm .env vào .gitignore, rồi viết scripts/thu-pg.ts:

import pg from 'pg';

const url = process.env.DATABASE_URL;
if (!url) throw new Error('Thiếu DATABASE_URL');

// 1. Mỗi truy vấn một kết nối mới
let t = performance.now();
for (let i = 0; i < 50; i++) {
  const client = new pg.Client({ connectionString: url });
  await client.connect();
  await client.query('SELECT 1');
  await client.end();
}
console.log('Kết nối mới:', Math.round(performance.now() - t), 'ms');

// 2. Cùng 50 truy vấn qua pool
const pool = new pg.Pool({ connectionString: url, max: 5 });
t = performance.now();
for (let i = 0; i < 50; i++) await pool.query('SELECT 1');
console.log('Pool:', Math.round(performance.now() - t), 'ms');

// 3. 50 truy vấn cùng lúc, pool chỉ có 5 kết nối
t = performance.now();
await Promise.all(Array.from({ length: 50 }, () => pool.query('SELECT pg_sleep(0.1)')));
console.log('50 truy vấn 0,1 giây cùng lúc, max 5:', Math.round(performance.now() - t), 'ms');

await pool.end();

Thêm "type": "module" vào package.json để dùng được await ở cấp ngoài cùng, rồi chạy npx tsx --env-file=.env scripts/thu-pg.ts. Trước khi chạy, ghi vào notes dự đoán của bạn cho dòng thứ ba. Gợi ý: 50 truy vấn, mỗi lần chạy được 5 truy vấn song song, mỗi truy vấn 0,1 giây.

Dòng cuối await pool.end() đóng mọi kết nối. Thiếu nó, script in xong kết quả nhưng không thoát, vì các kết nối còn mở giữ tiến trình sống. Trong server thì bạn không gọi end(), vì pool sống cùng tiến trình.

max bao nhiêu là vừa

Không phải càng to càng nhanh. Database chỉ có vài nhân CPU. 100 kết nối cùng chạy thì chúng tranh nhau CPU và đĩa, và từng truy vấn chậm đi. Một pool nhỏ xếp hàng ở phía Node thường cho tổng thời gian tốt hơn. Điểm khởi đầu hợp lý là 10.

Điều cần nhớ là phép nhân: 3 bản app chạy song song, mỗi bản max: 10, là 30 kết nối. Trên serverless, mỗi lần hàm chạy có thể là một bản app mới với pool riêng, nên con số này tăng rất nhanh. Đó là lý do các dịch vụ Postgres cho serverless đều có thêm một bộ gom kết nối đứng trước, như PgBouncer. Tuần 8 khi deploy bạn sẽ gặp lại chuyện này.

Bút đỏ: những câu nghe đúng mà sai

"Mở kết nối trong handler, xong thì đóng, cho sạch."Mỗi request phải trả chi phí mở kết nối, và lúc đông người thì chạm giới hạn max_connections. Tạo một pool duy nhất khi app khởi động và dùng chung.

"Pool max càng lớn thì càng chịu được nhiều người."Database có giới hạn CPU và số kết nối. Pool vừa phải cộng hàng đợi thường nhanh hơn. Nhân max với số bản app đang chạy.

"Không đặt connectionTimeoutMillis cũng được, mặc định chắc hợp lý."Mặc định là 0, tức là chờ mãi. Khi pool cạn, request treo thay vì báo lỗi. Đặt vài giây.

Tự kiểm tra

Tự trả lời trước, rồi mới bấm mở đáp án.

Tạo new Pool() bên trong mỗi handler có vấn đề gì?

Mỗi request tạo pool mới, nên mất hết lợi ích dùng lại và số kết nối tăng không giới hạn. Tạo một pool cho cả app.

Dùng pool.connect() mà quên client.release(). Chuyện gì xảy ra?

Kết nối không được trả lại. Sau max lần, mọi request đứng chờ mãi.

Vì sao chuỗi kết nối để trong .env, không viết vào code?

Nó chứa mật khẩu database, và khác nhau giữa máy bạn, máy test, server.

Câu hỏi phỏng vấn

Connection pool là gì, vì sao cần?

Pool là một nhóm kết nối tới database được mở sẵn và dùng lại. Mở kết nối tới PostgreSQL tốn thời gian vì phải bắt tay TCP, xác thực và tạo một tiến trình mới trên server, và số kết nối có giới hạn. Với pool, mỗi request mượn một kết nối đang mở, chạy xong thì trả lại. Khi pool bận hết, request xếp hàng thay vì mở thêm, nên database không bị quá tải.

Bạn chọn kích thước pool thế nào?

Tôi bắt đầu nhỏ, khoảng 10, rồi đo. Database có số nhân CPU giới hạn, nên quá nhiều kết nối chạy cùng lúc làm từng truy vấn chậm đi. Tôi cũng nhân kích thước pool với số bản app đang chạy để chắc tổng không vượt max_connections của database, và chừa chỗ cho migration và công cụ quản trị. Nếu chạy serverless, tôi đặt một bộ gom kết nối như PgBouncer ở trước database.

Lỗi rò kết nối là gì, bạn phát hiện thế nào?

Là khi code mượn kết nối từ pool mà không trả lại, thường do quên release ở nhánh lỗi. Pool cạn dần, rồi mọi request đứng chờ cho tới khi hết thời gian. Tôi phòng bằng cách luôn release trong finally, hoặc gói việc mượn và trả vào một hàm dùng chung. Để phát hiện, tôi theo dõi số kết nối đang được mượn và số request đang chờ của pool, và đặt connectionTimeoutMillis để lỗi hiện ra thay vì treo im lặng.

Nhớ 3 ý

  1. Driver pg nói chuyện với Postgres; một pool cho cả app.
  2. pool.query cho câu đơn lẻ; pool.connect khi cần nhiều câu trên cùng kết nối, nhớ release().
  3. Chuỗi kết nối nằm trong .env; max nhỏ thôi là đủ.
