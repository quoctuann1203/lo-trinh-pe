Trong một câu

Transaction gom nhiều câu SQL thành một thao tác: hoặc tất cả cùng thành công, hoặc không câu nào có hiệu lực. Không bao giờ có chuyện làm được một nửa.

Hình dung chuyển khoản ngân hàng: trừ tiền tài khoản A và cộng tiền tài khoản B phải xảy ra cùng nhau. Mất điện giữa chừng mà A đã bị trừ còn B chưa được cộng là không chấp nhận được. Transaction đảm bảo hai bước đó dính liền.

Vì sao cần transaction

Nhiều việc trong app là vài câu SQL liền nhau: tạo lớp rồi thêm 20 học sinh, ghi khoản đóng rồi cập nhật trạng thái hoá đơn. Lỗi xảy ra ở câu giữa thì dữ liệu nằm ở trạng thái nửa vời mà không ai cố ý tạo ra, và rất khó dọn. Transaction cho bạn một nút "huỷ hết" tự động.

Từ khoá cần biết

BEGIN
Mở một transaction.
COMMIT
Chốt: mọi thay đổi trong transaction có hiệu lực cùng lúc.
ROLLBACK
Huỷ: mọi thay đổi trong transaction biến mất như chưa từng chạy.
ACID
Bốn lời hứa của transaction: trọn vẹn (Atomicity), đúng quy tắc (Consistency), không thấy việc dở của nhau (Isolation), bền khi đã chốt (Durability).
Cùng một kết nối
Mọi câu trong một transaction phải chạy trên đúng một kết nối, nên dùng pool.connect().
Kiểu Db
Kiểu chung cho pool và client, để hàm store chạy được cả trong lẫn ngoài transaction.

Transaction hoạt động thế nào

  1. Mượn một kết nối từ pool bằng pool.connect().
  2. BEGIN: từ đây mọi thay đổi chỉ người trong transaction thấy.
  3. Chạy các câu SQL lần lượt trên chính kết nối đó.
  4. Tất cả ổn thì COMMIT; có lỗi thì ROLLBACK.
  5. Trả kết nối bằng release() trong khối finally, dù thành công hay thất bại.

Một thao tác, nhiều câu SQL

Giáo viên mở lớp mới và thêm luôn 20 học sinh. Trong database đó là hai bước: tạo một dòng classes, rồi tạo 20 dòng enrollments. Giả sử bước hai lỗi ở học sinh thứ 13, vì id học sinh sai. Không có transaction thì lớp đã được tạo, 12 học sinh đã vào lớp, 8 học sinh thì không. Giáo viên bấm "thử lại" thì lỗi "lớp đã tồn tại". Không ai thiết kế trạng thái đó, nhưng nó nằm trong database của bạn.

Transaction gói nhiều câu lệnh thành một đơn vị: hoặc tất cả có hiệu lực, hoặc không câu nào có.

BEGIN;
INSERT INTO classes (teacher_id, name, monthly_fee) VALUES (1, 'Toán 9A', 800000) RETURNING id;
INSERT INTO enrollments (class_id, student_id) VALUES (7, 1), (7, 2), (7, 999999);
-- ERROR:  insert or update on table "enrollments" violates foreign key constraint
ROLLBACK;
-- Lớp 'Toán 9A' không còn: như chưa từng có gì xảy ra

PostgreSQL chạy mỗi câu lệnh lẻ trong một transaction riêng, tự động. Một câu UPDATE sửa 1.000 dòng sẽ sửa cả 1.000 hoặc không dòng nào. Bạn chỉ cần viết BEGIN khi muốn nhiều câu cùng chung số phận.

Làm thử: lỗi giữa chừng thì sao

Thử trong psql: BEGIN, một câu lỗi, rồi một câu đúng.

BEGIN;
INSERT INTO teachers (name, phone) VALUES ('Cô Lan', '0900000001');   -- số đã có: lỗi 23505
SELECT 1;
-- ERROR:  current transaction is aborted, commands ignored until end of transaction block
ROLLBACK;

Sau một lỗi, PostgreSQL từ chối mọi câu tiếp theo trong transaction đó cho tới khi bạn ROLLBACK. Gõ COMMIT lúc này cũng chỉ được kết quả ROLLBACK. Không có cách nào "bỏ qua lỗi rồi commit phần còn lại". Đó chính là atomicity.

Transaction trong Node: phải cùng một kết nối

Đây là lỗi hay gặp nhất khi mới dùng pool:

// SAI: mỗi pool.query có thể đi một kết nối khác
await pool.query('BEGIN');
await pool.query('INSERT INTO classes ...');
await pool.query('INSERT INTO enrollments ...');
await pool.query('COMMIT');

Transaction thuộc về một kết nối. BEGIN có thể chạy trên kết nối số 1, hai câu INSERT trên kết nối số 2 và 3, mỗi câu tự commit ngay. COMMIT lại rơi vào một kết nối khác nữa. Code chạy không lỗi, nhưng không có transaction nào cả. Tệ hơn, kết nối số 1 bị trả về pool khi đang mở dở một transaction, và request sau mượn phải nó.

Cách đúng là mượn một kết nối, giữ nó suốt transaction, rồi trả lại. Viết một lần thành hàm dùng chung, để không ai phải nhớ thứ tự BEGIN, COMMIT, ROLLBACK, release:

// src/lib/db/tx.ts
import type pg from 'pg';
import { pool } from './pool';

/** Thứ chạy được truy vấn: cả pool lẫn một kết nối đang trong transaction. */
export type Db = pg.Pool | pg.PoolClient;

export async function withTransaction<T>(fn: (tx: pg.PoolClient) => Promise<T>): Promise<T> {
  const client = await pool.connect();
  let broken = false;
  try {
    await client.query('BEGIN');
    const result = await fn(client);
    await client.query('COMMIT');
    return result;
  } catch (err) {
    try {
      await client.query('ROLLBACK');
    } catch {
      broken = true;      // ROLLBACK cũng lỗi: kết nối đã hỏng
    }
    throw err;
  } finally {
    client.release(broken);   // true: huỷ kết nối thay vì trả nó về pool
  }
}

Đọc từng phần:

  • finally luôn trả kết nối, dù thành công hay lỗi. Không có nó là rò kết nối, bài Thứ Ba.
  • release(true) khi ROLLBACK cũng thất bại, thường vì mất kết nối mạng. Một kết nối như vậy không được trả về pool cho request khác dùng.
  • Lỗi gốc luôn được ném tiếp. Người gọi cần biết vì sao transaction thất bại, để chọn trả 409 hay 500.

Hàm store nhận Db

Hàm store cần chạy được cả bên ngoài lẫn bên trong transaction. Cho nó nhận tham số db:

export async function createClass(db: Db, input: { teacherId: number; name: string; monthlyFee: number }) {
  const { rows } = await db.query<{ id: number }>(
    'INSERT INTO classes (teacher_id, name, monthly_fee) VALUES ($1, $2, $3) RETURNING id',
    [input.teacherId, input.name, input.monthlyFee],
  );
  return rows[0].id;
}

export async function enroll(db: Db, classId: number, studentIds: number[]) {
  await db.query(
    'INSERT INTO enrollments (class_id, student_id) SELECT $1, unnest($2::bigint[])',
    [classId, studentIds],
  );
}

// Dùng: hai hàm, một transaction
const classId = await withTransaction(async (tx) => {
  const id = await createClass(tx, { teacherId, name: 'Toán 9A', monthlyFee: 800_000 });
  await enroll(tx, id, studentIds);
  return id;
});

unnest($2::bigint[]) biến mảng thành nhiều dòng, nên 20 học sinh vào lớp chỉ bằng một câu lệnh. Một câu lệnh thì đã tự là một transaction, nhưng createClass với enroll là hai câu, nên vẫn cần withTransaction.

Giữ transaction ngắn

Trong lúc transaction còn mở, các dòng nó đã sửa bị khoá. Ai muốn sửa chúng phải chờ. Kết nối nó đang giữ cũng không cho ai khác mượn được. Vì vậy, bên trong withTransaction chỉ có các câu SQL:

// SAI: gọi mạng bên trong transaction
await withTransaction(async (tx) => {
  await recordPayment(tx, ...);
  await sendZaloMessage(parentPhone, 'Đã nhận học phí');   // mất 2 giây, có khi 30 giây
});

Nếu dịch vụ tin nhắn chậm 30 giây, hoá đơn đó bị khoá 30 giây và một kết nối của pool bị chiếm 30 giây. Còn nếu tin nhắn gửi đi rồi mà COMMIT lại lỗi, phụ huynh nhận tin "đã nhận tiền" cho một khoản không có trong database. Gửi tin sau khi transaction đã commit. Tuần 34 bạn sẽ học cách làm việc này chắc chắn hơn bằng hàng đợi.

Bút đỏ: những câu nghe đúng mà sai

"Gọi pool.query('BEGIN') rồi các câu sau là nằm trong transaction."Mỗi pool.query có thể dùng một kết nối khác. Mượn một client bằng pool.connect() và chạy mọi câu trên client đó.

"Câu thứ hai lỗi thì COMMIT phần đã chạy được."Sau một lỗi, PostgreSQL từ chối mọi câu cho tới khi ROLLBACK, và COMMIT cũng thành ROLLBACK. Muốn giữ một phần thì phải dùng SAVEPOINT, và hiếm khi cần.

"Gói cả việc gửi email vào transaction cho chắc."Transaction chỉ hoàn tác được dữ liệu trong database. Email đã gửi thì không lấy lại được, và trong lúc chờ mạng thì dòng bị khoá. Gửi sau khi commit.

Tự kiểm tra

Tự trả lời trước, rồi mới bấm mở đáp án.

Viết await pool.query('BEGIN'), rồi await pool.query('INSERT ...'), rồi await pool.query('COMMIT'). Sai ở đâu?

Mỗi pool.query có thể chạy trên một kết nối khác nhau, nên các câu không nằm trong cùng transaction. Dùng pool.connect() và chạy cả ba trên một client.

Trong transaction, câu thứ 3 trên 5 câu bị lỗi và bạn ROLLBACK. Hai câu đầu còn hiệu lực không?

Không. ROLLBACK huỷ mọi thay đổi kể từ BEGIN.

Vì sao không nên gọi API bên ngoài (gửi email, ngân hàng) ở giữa một transaction?

Transaction giữ khoá trong lúc chờ mạng, chặn người khác; và nếu rollback thì không thu hồi được email đã gửi. Giữ transaction ngắn, làm việc bên ngoài sau khi commit.

Câu hỏi phỏng vấn

Transaction là gì? Kể một chỗ bạn đã dùng.

Transaction gói nhiều câu lệnh thành một đơn vị: hoặc tất cả có hiệu lực, hoặc không câu nào có. Trong công cụ học phí, tạo lớp và thêm học sinh vào lớp là hai câu INSERT. Tôi chạy chúng trong một transaction để nếu một học sinh không hợp lệ thì lớp cũng không được tạo, và giáo viên không bị kẹt với một lớp nửa vời.

Bạn quản lý transaction thế nào khi dùng connection pool?

Transaction gắn với một kết nối, nên tôi mượn một client từ pool, chạy BEGIN, các câu lệnh và COMMIT trên đúng client đó, ROLLBACK nếu có lỗi, và luôn trả client trong finally. Tôi gói việc này thành một hàm withTransaction nhận callback, để không ai phải tự viết lại và không ai lỡ dùng pool.query bên trong transaction.

Vì sao nên giữ transaction ngắn?

Vì trong lúc transaction mở, các dòng nó đã sửa bị khoá và một kết nối của pool bị chiếm. Transaction dài làm request khác phải chờ và có thể làm cạn pool. Tôi không gọi mạng ra ngoài bên trong transaction. Việc như gửi email chỉ làm sau khi commit, vì database không thể hoàn tác một email đã gửi.

Nhớ 3 ý

  1. Transaction: nhiều câu SQL thành một thao tác, tất cả hoặc không gì cả.
  2. BEGIN, các câu SQL, rồi COMMIT hoặc ROLLBACK, trên cùng một kết nối từ pool.connect().
  3. Luôn release() trong finally; giữ transaction ngắn.
