Vấn đề không nằm ở SQL, mà ở khoá

Hầu hết lệnh ALTER TABLE cần khoá mạnh nhất của PostgreSQL trên bảng đó, gọi là ACCESS EXCLUSIVE. Trong lúc giữ khoá, không ai đọc hay ghi được bảng. Nếu lệnh chỉ đổi thông tin mô tả bảng, khoá được giữ vài mili giây và không ai nhận ra. Nếu lệnh phải đọc hay viết lại mọi dòng, khoá được giữ đúng bằng thời gian đó: vài giây với một triệu dòng, vài phút với một trăm triệu dòng.

Còn một cái bẫy tệ hơn: hàng đợi khoá. Thử với ba cửa sổ psql:

-- Cửa sổ 1: một transaction đang đọc, chưa kết thúc
BEGIN;
SELECT count(*) FROM students;

-- Cửa sổ 2: migration muốn thêm cột. Lệnh này đứng chờ cửa sổ 1
ALTER TABLE students ADD COLUMN nickname text;

-- Cửa sổ 3: một người dùng chỉ muốn đọc. Lệnh này cũng đứng chờ!
SELECT name FROM students LIMIT 1;

Cửa sổ 3 chỉ cần khoá đọc, vốn không xung đột với cửa sổ 1. Nhưng nó phải xếp hàng sau lệnh ALTER đang chờ. Một lệnh ALTER lẽ ra chạy trong 1 mili giây, chỉ vì chờ một transaction chậm, đã làm cả bảng đứng im. Gõ COMMIT ở cửa sổ 1 và xem hai cửa sổ kia chạy tiếp.

lock_timeout: thà thất bại còn hơn chặn mọi người

Lặp lại thí nghiệm, nhưng ở cửa sổ 2 đặt giới hạn thời gian chờ khoá:

SET lock_timeout = '2s';
ALTER TABLE students ADD COLUMN nickname text;
-- ERROR:  canceling statement due to lock timeout

Sau 2 giây lệnh tự huỷ, hàng đợi được giải phóng, người dùng không bị ảnh hưởng thêm. Bạn chạy lại migration vào lúc khác. Trong file migration của dbmate, mọi thứ đã nằm trong một transaction, nên dùng SET LOCAL để giới hạn chỉ áp dụng cho transaction đó:

-- migrate:up
SET LOCAL lock_timeout = '3s';
ALTER TABLE students ADD COLUMN nickname text;

Migration thất bại vì lock_timeout là chuyện bình thường và an toàn: transaction được hoàn tác, không có gì thay đổi.

Lệnh nào nhanh, lệnh nào chậm

Bảng này đúng với PostgreSQL 18. Phiên bản cũ có thể khác, và bạn sẽ đọc thấy nhiều lời khuyên cũ trên mạng.

Có thể tự kiểm tra một lệnh có viết lại bảng không: SELECT pg_relation_filenode('invoices') trước và sau lệnh. Con số đổi tức là Postgres đã tạo file dữ liệu mới, tức là đã viết lại toàn bộ bảng.

NOT VALID rồi VALIDATE

-- Bước 1: tức thì. Ràng buộc có hiệu lực ngay với dòng MỚI, chưa kiểm tra dòng cũ
ALTER TABLE invoices
  ADD CONSTRAINT invoices_discount_check CHECK (discount >= 0 AND discount < amount) NOT VALID;

-- Bước 2: quét dòng cũ, nhưng chỉ giữ khoá nhẹ, đọc ghi vẫn chạy bình thường
ALTER TABLE invoices VALIDATE CONSTRAINT invoices_discount_check;

Nếu bước 2 báo lỗi, tức là có dòng cũ vi phạm. Sửa dữ liệu đó rồi chạy lại bước 2. Ràng buộc vẫn bảo vệ dữ liệu mới trong lúc bạn sửa.

CREATE INDEX CONCURRENTLY

Tạo index mà không chặn lệnh ghi, đổi lại chậm hơn khoảng hai lần. Lệnh này không được chạy trong transaction:

BEGIN;
CREATE INDEX CONCURRENTLY students_name_idx ON students (name);
-- ERROR:  CREATE INDEX CONCURRENTLY cannot run inside a transaction block

Vì vậy file migration chứa nó phải tắt transaction của dbmate, và chỉ nên chứa đúng một lệnh đó. Nếu lệnh thất bại giữa chừng, nó để lại một index ở trạng thái INVALID. Phải DROP INDEX rồi chạy lại.

-- migrate:up transaction:false
CREATE INDEX CONCURRENTLY payments_invoice_id_idx ON payments (invoice_id);

-- migrate:down transaction:false
DROP INDEX CONCURRENTLY payments_invoice_id_idx;

Expand và contract

Khoá chỉ là một nửa vấn đề. Nửa còn lại: lúc deploy, có một khoảng thời gian code cũ vẫn chạy trên schema mới. Đổi tên cột parent_phone thành phone mất 1 mili giây, nhưng mọi request của code cũ có SELECT parent_phone sẽ lỗi cho tới khi code mới lên xong.

Expand và contract tách một thay đổi phá vỡ thành nhiều bước, mỗi bước tương thích với cả code cũ lẫn code mới:

BướcSchemaCode
1. ExpandThêm cấu trúc mới bên cạnh cấu trúc cũ. Chép dữ liệu cũ sang (backfill)Code cũ vẫn chạy, không biết gì về phần mới
2. Chuyển ghiCode ghi vào cả hai nơi
3. Chuyển đọcCode chỉ đọc nơi mới. Kiểm tra mọi thứ ổn
4. ContractBỏ cấu trúc cũCode chỉ còn biết nơi mới

Mỗi bước là một lần deploy riêng, có thể cách nhau vài ngày. Nếu bước 3 có vấn đề, bạn quay lại bước 2 mà không mất gì, vì dữ liệu cũ vẫn còn nguyên. Chỉ bước 4 là không quay lại được, nên nó luôn là bước cuối và làm khi đã chắc chắn.

Hôm nay hocphi chưa có code nào đọc database, đó là việc của tuần 5. Bạn sẽ làm bước 1 và bước 4 trong hai migration riêng, và ghi vào notes code ở bước 2, 3 sẽ phải làm gì.

Backfill trên bảng lớn

Một câu UPDATE trên 2.000 dòng chạy trong chớp mắt. Trên 10 triệu dòng, nó giữ khoá ghi trên từng dòng tới khi transaction kết thúc, và tạo ra một transaction khổng lồ. Với bảng lớn, backfill làm theo từng lô nhỏ, mỗi lô một transaction, ngoài migration:

UPDATE students s
SET parent_id = p.id
FROM parents p
WHERE p.phone = s.parent_phone
  AND s.parent_id IS NULL
  AND s.id BETWEEN 1 AND 10000;   -- lô tiếp theo: 10001 tới 20000...

Với dữ liệu của hocphi bây giờ thì chưa cần. Biết là có cách này để nói được khi phỏng vấn.

Bút đỏ: những câu nghe đúng mà sai

"Thêm cột có DEFAULT trên bảng lớn sẽ khoá bảng rất lâu."Đúng với PostgreSQL trước bản 11. Từ bản 11, default là hằng số hay now() thì tức thì. Chỉ hàm cho mỗi dòng một giá trị khác nhau mới viết lại bảng.

"Lệnh ALTER chạy nhanh thì không ảnh hưởng ai."Nếu nó phải chờ khoá, mọi truy vấn đến sau xếp hàng sau nó, kể cả SELECT. Luôn đặt lock_timeout.

"Đổi tên cột là thay đổi nhỏ."Với database thì nhỏ, với code đang chạy thì là phá vỡ. Thêm cột mới, chuyển code, rồi mới bỏ cột cũ.

Câu hỏi phỏng vấn

Bạn đổi tên một cột trên production thế nào mà không có downtime?

Theo expand và contract. Thêm cột mới và chép dữ liệu sang. Deploy code ghi vào cả hai cột. Deploy code chỉ đọc cột mới. Khi chắc chắn không còn gì dùng cột cũ, viết migration xoá nó. Mỗi bước tương thích với cả phiên bản code trước và sau nó, nên lúc deploy không có request nào lỗi, và trước bước cuối luôn quay lại được.

Một migration chạy nhanh trên máy bạn lại làm production treo vài phút. Vì sao?

Có hai khả năng. Lệnh đó quét hoặc viết lại cả bảng, chạy nhanh trên dữ liệu mẫu nhưng chậm trên bảng thật, trong lúc giữ khoá chặn mọi truy cập. Hoặc lệnh phải chờ một transaction dài đang chạy, và mọi truy vấn đến sau xếp hàng sau nó. Cách phòng là biết lệnh nào viết lại bảng, dùng các phiên bản không chặn như CONCURRENTLY hay NOT VALID, và đặt lock_timeout để migration tự huỷ thay vì chặn mọi người.

Thêm ràng buộc vào bảng lớn thế nào cho an toàn?

Thêm ràng buộc với NOT VALID: việc này tức thì, và ràng buộc có hiệu lực ngay với dữ liệu mới. Sau đó chạy VALIDATE CONSTRAINT để kiểm tra dữ liệu cũ. Bước này quét bảng nhưng chỉ giữ khoá nhẹ, nên đọc ghi vẫn chạy. Index thì dùng CREATE INDEX CONCURRENTLY, chạy ngoài transaction.
