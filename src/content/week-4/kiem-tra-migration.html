Migration sai theo những cách nào

Migration của bạn chạy được trên máy bạn, vì database của bạn đã đi qua đúng các bước bạn đã làm, kể cả những lệnh gõ tay trong psql mà bạn quên mất. Database của đồng đội, của CI, của server thì không có các bước đó. Những lỗi hay gặp nhất:

LỗiHậu quả
Migration dựa vào thứ đã tạo bằng tay, không có trong migration nàoChạy trên database trống thì lỗi
Phần down thiếu một bước, như quên DROP TABLEDown chạy được, nhưng up lại thì báo already exists
Down không trả schema về đúng như trước upQuay lại rồi đi tiếp thì ra một schema khác
Quên commit db/schema.sql sau khi thêm migrationNgười review thấy một schema đã cũ

Cả bốn lỗi đều bắt được tự động bằng một quy trình: tạo database trống, chạy lên, rollback hết, chạy lên lại, và so schema ở mỗi bước với file đã commit.

scripts/db-check.sh

#!/usr/bin/env bash
# Kiểm tra migration trên một database riêng tên hocphi_check, không đụng dữ liệu dev.
set -euo pipefail

CHECK_URL='postgres://hocphi:hocphi@db:5432/hocphi_check?sslmode=disable'
dm() {
  docker compose run --rm -T -e DATABASE_URL="$CHECK_URL" dbmate \
    --schema-file /db/schema.check.sql "$@"
}
trap 'rm -f db/schema.check.sql' EXIT

echo "1. Tạo database trống và chạy mọi migration"
dm drop
dm up

echo "2. So với db/schema.sql đã commit"
diff -u db/schema.sql db/schema.check.sql

echo "3. Rollback từng migration cho tới hết"
count=$(ls db/migrations/*.sql | wc -l | tr -d " ")
for _ in $(seq "$count"); do dm down; done

echo "4. Chạy lại từ đầu, schema phải y như cũ"
dm up
diff -u db/schema.sql db/schema.check.sql

echo "OK: $count migration chạy lên, xuống, lên lại đều khớp"

Đọc từng phần:

  • set -euo pipefail: dừng ngay khi có lệnh lỗi. Không có dòng này thì script vẫn in "OK" sau khi diff đã báo khác.
  • Database hocphi_check riêng: dm drop xoá database đó, không đụng tới dữ liệu bạn đang dùng để phát triển. Ghi đè DATABASE_URL bằng -e cho riêng lần chạy này.
  • --schema-file /db/schema.check.sql: dbmate ghi bản dump ra một file khác, để so với db/schema.sql thật. trap ... EXIT xoá file đó khi script kết thúc, kể cả khi lỗi.
  • Bước 2 bắt lỗi quên commit schema, và lỗi migration dựa vào thứ không có trong migration.
  • Bước 3 và 4 bắt lỗi down thiếu bước hoặc không trả về đúng.

Chạy bằng npm run db:check. Lần đầu sẽ thấy nhiều dòng của Docker và dbmate, dòng cuối phải là:

OK: 5 migration chạy lên, xuống, lên lại đều khớp

Cố tình làm hỏng để tin script

Một bài kiểm tra chưa từng báo lỗi thì chưa chắc đã kiểm tra được gì. Giống như ở tuần 2 bạn làm test thất bại trước khi tin nó. Thử ba cách làm hỏng, mỗi lần xong thì sửa lại:

  1. Xoá dòng DROP TABLE parents; trong phần down của migration tách phụ huynh. Script dừng ở bước 4: Error: pq: relation "parents" already exists (42P07).
  2. Tạo một migration mới thêm cột parents.note, nhưng chưa chạy npm run db:migrate trên database dev. Script dừng ở bước 2, và diff chỉ ra hai chỗ schema.sql đang thiếu: cột note text và số version của migration mới.
  3. Trong psql của database dev, gõ tay CREATE TABLE notes (id int), rồi viết một migration có ALTER TABLE notes .... npm run db:migrate chạy được, nhưng db:check thì không. Đó chính là lỗi "chạy được trên máy tôi".

Những gì script không bắt được

Script chạy trên database trống, nên nó không thấy được ba thứ quan trọng nhất trên server thật:

  • Thời gian và khoá. Một lệnh viết lại bảng mất 1 mili giây trên bảng trống.
  • Dữ liệu cũ không hợp lệ. Như lỗi down của archive_classes bạn gặp ở bài trước.
  • Backfill sai. Bảng trống thì không có gì để chép sai.

Hai lớp bảo vệ còn lại là người đọc migration trước khi gộp, và chạy thử trên một bản sao dữ liệu đủ lớn.

Danh sách review một migration

Dùng danh sách này khi tự review, và khi nhờ AI review:

HỏiNếu không

Có SET LOCAL lock_timeout chưa?Thêm vào đầu migration

Có backfill không? Có câu kiểm tra kết quả chưa?Viết câu kiểm tra với kết quả biết trước

Video tuần này nói về một lỗi khác mà database trống không bao giờ lộ ra: deadlock. Nó xảy ra khi migration khoá hai bảng theo thứ tự ngược với transaction của ứng dụng. Cách phòng là giữ mỗi migration nhỏ, đụng tới ít bảng, và luôn có lock_timeout.

Đưa vào CI sau

Ở tuần 17 bạn sẽ dựng GitHub Actions. Lúc đó npm run db:check chạy trên mọi pull request, và không ai gộp được một migration hỏng. Hôm nay chỉ cần chạy nó trước mỗi lần commit migration.

Bút đỏ: những câu nghe đúng mà sai

"Migration chạy được trên máy tôi rồi."Database của bạn có lịch sử mà nơi khác không có. Chỉ tin migration khi nó chạy được từ database trống.

"db:check xanh là migration an toàn để chạy trên production."Nó chỉ chứng minh migration đúng về cấu trúc. Khoá, thời gian chạy và dữ liệu cũ cần người review và chạy thử trên bản sao dữ liệu.

"Script kiểm tra không báo lỗi lần nào, chứng tỏ migration tốt."Hoặc script không kiểm tra gì. Làm hỏng có chủ đích một lần để thấy nó báo lỗi.

Câu hỏi phỏng vấn

Bạn kiểm tra migration trước khi gộp thế nào?

Tự động, tôi có một script chạy trên database trống: chạy mọi migration, so schema với file đã commit, rollback hết, chạy lại, rồi so lần nữa. Script đó bắt được migration dựa vào trạng thái không có trong repo và down viết thiếu. Bằng tay, tôi review theo danh sách: có lệnh nào khoá bảng lâu không, có lock_timeout chưa, code cũ có chạy được với schema mới không, backfill có câu kiểm tra chưa. Với migration lớn, tôi chạy thử trên bản sao dữ liệu thật để đo thời gian.

Vì sao phải kiểm tra migration trên database trống?

Vì database trên máy lập trình viên có lịch sử riêng: lệnh gõ tay, migration đã sửa sau khi chạy, nhánh khác đã chạy rồi bỏ. Migration chạy được ở đó chưa chắc chạy được ở CI hay trên máy người mới. Database trống là trạng thái duy nhất mà mọi người đều có giống nhau.

Có những rủi ro nào mà kiểm tra trên database trống không phát hiện được?

Thời gian chạy và khoá, vì bảng trống thì lệnh nào cũng nhanh. Dữ liệu cũ vi phạm ràng buộc mới. Backfill nối sai điều kiện. Deadlock với transaction của ứng dụng. Những rủi ro này cần review, chạy thử trên bản sao dữ liệu có kích thước thật, và dùng lock_timeout để migration tự huỷ thay vì chặn người dùng.
