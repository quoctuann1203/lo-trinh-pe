Vì sao không sửa schema.sql nữa

Ở tuần 3, mỗi lần đổi schema bạn sửa schema.sql rồi chạy lại từ đầu, vì file bắt đầu bằng DROP TABLE. Cách đó chỉ đúng khi dữ liệu không quan trọng. Khi đã có giáo viên dùng thật, xoá bảng là mất sổ thu tiền của họ.

Cách thứ hai là mở psql trên server và gõ ALTER TABLE bằng tay. Một tháng sau không ai nhớ đã gõ gì. Máy bạn, máy đồng đội và server lệch nhau, và lỗi chỉ hiện ra khi deploy.

Migration giải quyết cả hai vấn đề. Mỗi thay đổi schema là một file SQL riêng, tên bắt đầu bằng thời điểm tạo:

db/migrations/
  20261203090000_create_books.sql
  20261203093000_books_author_set_null.sql
  20261203100000_add_updated_at.sql

Database giữ một bảng schema_migrations ghi lại file nào đã chạy. Lệnh up chạy những file chưa có trong bảng đó, theo thứ tự tên. Database ở đâu cũng đi qua đúng các bước giống nhau, theo đúng thứ tự.

dbmate: công cụ migration bằng SQL thuần

Có rất nhiều công cụ migration. Nhiều cái gắn với một ORM, bạn viết schema bằng TypeScript rồi công cụ sinh SQL. Tuần này dùng dbmate vì bạn viết thẳng SQL, đúng thứ bạn vừa học ở tuần 3, và nó không phụ thuộc ngôn ngữ của ứng dụng. Chạy nó bằng Docker nên không cần cài gì thêm. Thêm vào compose.yaml của sql-practice:

services:
  db:
    # ... giữ nguyên như tuần 3

  dbmate:
    image: ghcr.io/amacneil/dbmate:2.38.2
    profiles: [tools]               # không tự chạy khi docker compose up
    environment:
      DATABASE_URL: postgres://hoc:hoc@db:5432/books?sslmode=disable
      DBMATE_WAIT: "true"           # đợi Postgres sẵn sàng rồi mới chạy
    volumes:
      - ./db:/db
    depends_on:
      - db

Hai điểm đáng chú ý. Thứ nhất, DATABASE_URL trỏ tới database books, không phải hoc. Database hoc đã có bảng tạo bằng tay từ tuần 3, còn books sẽ được dbmate tạo mới. Thứ hai, @db:5432 dùng tên service db, vì dbmate chạy trong cùng mạng Docker với Postgres.

docker compose run --rm dbmate new create_booksTạo file migration trống, tên có thời điểm hiện tại

Gõ docker compose run --rm dbmate mãi thì dài. Ở repo hocphi hôm Thứ Bảy bạn sẽ gói chúng vào script npm.

Chạy lệnh new, mở file vừa sinh ra, và chép schema sách của tuần 3 vào. Lần này không có DROP TABLE ở đầu:

Hai dòng chú thích -- migrate:up và -- migrate:down là cú pháp của dbmate, không phải tuỳ chọn. Phần down làm ngược lại phần up, và theo thứ tự ngược lại: bảng con bị xoá trước bảng cha.

docker compose run --rm dbmate up
# Applying: 20261203090000_create_books.sql
# Applied: 20261203090000_create_books.sql in 14ms
# Writing: ./db/schema.sql

docker compose run --rm dbmate status
# [X] 20261203090000_create_books.sql
#
# Applied: 1
# Pending: 0

Vào psql xem tận mắt: docker compose exec db psql -U hoc -d books, rồi \dt và SELECT * FROM schema_migrations;. Bảng đó chỉ có một cột version chứa phần số ở đầu tên file.

db/schema.sql: ảnh chụp schema sau mỗi lần chạy

Sau mỗi lần up hay down, dbmate gọi pg_dump và ghi toàn bộ schema hiện tại ra db/schema.sql. Image Docker của dbmate có sẵn pg_dump bản 18, nên bạn không phải cài. File này nên được commit, vì hai lý do:

  • Muốn biết bảng books bây giờ có những cột nào, đọc một file thay vì cộng mười migration lại trong đầu.
  • Khi review pull request, phần diff của schema.sql cho thấy chính xác schema đã đổi gì, kể cả những thứ bạn không cố ý đổi.

Không bao giờ sửa schema.sql bằng tay. Nó là kết quả, không phải nguồn.

Mỗi migration chạy trong một transaction

dbmate bọc mỗi file trong BEGIN và COMMIT. Nếu câu lệnh thứ ba trong file lỗi, hai câu đầu cũng được hoàn tác, và file không được ghi vào schema_migrations. Bạn sửa file rồi chạy lại. Không bao giờ có chuyện migration chạy được một nửa.

Có một số lệnh PostgreSQL không được chạy trong transaction, như CREATE INDEX CONCURRENTLY. Với những file đó, viết -- migrate:up transaction:false. Thứ Bảy bạn sẽ gặp trường hợp này.

Bốn quy tắc

  1. Đã chạy ở nơi khác thì không sửa nữa. Đã push lên và có người chạy rồi, sửa file cũ không có tác dụng gì với database của họ, vì schema_migrations đã ghi là xong. Muốn đổi tiếp thì viết migration mới.
  2. Một migration, một thay đổi có nghĩa. "Thêm cột updated_at" là một migration. "Đủ thứ sửa trong tuần" thì không. File nhỏ dễ review, và down dễ viết.
  3. Luôn viết down, và chạy thử nó. Down là cách bạn quay lại trên máy mình khi viết sai. Trên server thật, người ta thường sửa bằng một migration mới thay vì chạy down, nhưng down vẫn phải chạy đúng.
  4. Dữ liệu mẫu không nằm trong migration. Migration chạy ở mọi môi trường, kể cả server thật. 20 cuốn sách mẫu nằm trong file seed riêng, chỉ chạy trên máy mình.

Bài luyện Thứ Năm

  1. Tạo migration create_books từ 02-schema.sql. Chạy up, status, down, status, up.
  2. Cố tình viết sai một câu ở giữa migration thứ hai, chạy up, rồi dùng \d kiểm tra rằng không có gì thay đổi.
  3. Chạy dbmate drop rồi up. Nếu lệnh up chạy từ database trống ra lỗi, migration của bạn đang dựa vào thứ không có trong migration.
  4. Đọc db/schema.sql. Tìm tên ràng buộc mà Postgres tự đặt cho khoá ngoại books.author_id. Bài tiếp theo sẽ cần đến nó.

Bút đỏ: những câu nghe đúng mà sai

"Migration chạy rồi mà sai, mở file ra sửa lại là được."Database đã ghi nhận file đó, nên sửa không có tác dụng ở những nơi đã chạy. Viết migration mới để sửa.

"Down migration không bao giờ dùng trên server, khỏi viết."Bạn dùng nó hằng ngày trên máy mình khi đang viết migration. Và chạy thử down là cách kiểm tra rằng up thật sự làm đúng như bạn nghĩ.

"Cho dữ liệu mẫu vào migration để ai chạy cũng có sẵn."Migration chạy cả trên server thật. Dữ liệu mẫu nằm trong file seed riêng.

Câu hỏi phỏng vấn

Database migration là gì, vì sao cần?

Migration là các file mô tả từng thay đổi schema, đánh số theo thứ tự và được quản lý trong Git cùng với code. Công cụ migration ghi lại trong database những file nào đã chạy, nên mỗi môi trường chỉ chạy phần còn thiếu. Nhờ vậy mọi database đi qua cùng các bước, thay đổi schema được review như code, và ai clone repo về cũng dựng lại được schema bằng một lệnh.

Một migration đã chạy trên production bị sai, bạn làm gì?

Tôi không sửa file cũ, vì production đã ghi nhận nó là đã chạy. Tôi viết một migration mới để sửa, kiểm tra nó trên bản sao dữ liệu, rồi deploy như bình thường. Chạy down trên production chỉ khi chắc chắn down không làm mất dữ liệu, mà với những thay đổi như xoá cột thì điều đó không đúng.

Vì sao commit cả file schema.sql do công cụ sinh ra?

Vì nó là ảnh chụp schema hiện tại, đọc một file nhanh hơn cộng dồn mọi migration. Khi review, diff của nó cho thấy chính xác migration đã làm gì với schema, kể cả tác dụng phụ ngoài ý muốn. Nó cũng giúp phát hiện khi database của ai đó lệch khỏi migration.
