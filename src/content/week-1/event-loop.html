Trong một câu

Event loop là vòng lặp của Node quyết định việc nào chạy tiếp theo: hết code đang chạy thì nó lấy việc đã sẵn sàng (hẹn giờ đến giờ, file đọc xong, request mới tới) ra chạy, cứ thế lặp mãi.

Hình dung người phục vụ quán phở ở bài trước. Anh ta có một cuốn sổ ghi các việc đang chờ: "bàn 3 phở xong", "bàn 5 gọi thêm trà". Mỗi lần rảnh tay, anh ta mở sổ, làm việc tiếp theo. Event loop chính là cuốn sổ và thói quen mở sổ đó.

Vì sao phải hiểu event loop

Nếu không hiểu, bạn sẽ gặp những chuyện "khó hiểu" như: setTimeout(fn, 0) không chạy ngay; console.log in ra sai thứ tự mình nghĩ; cả server bỗng chậm 2 giây với mọi người dù database vẫn nhanh. Cả ba đều giải thích được bằng một quy tắc: JS chỉ chạy một việc mỗi lúc, và event loop chọn việc tiếp theo theo một thứ tự cố định.

Từ khoá cần biết

Call stack
Chồng các hàm đang chạy. Gọi hàm thì đặt lên đỉnh, hàm chạy xong thì lấy ra.
Callback
Hàm bạn đưa cho người khác gọi sau, ví dụ hàm truyền vào setTimeout.
Hàng đợi
Danh sách callback đã sẵn sàng, chờ tới lượt chạy.
Macrotask
Việc lớn được xử lý theo từng pha: callback của hẹn giờ, của I/O, của setImmediate.
Microtask
Việc nhỏ chạy ngay sau việc hiện tại: .then của promise, code sau await, process.nextTick.
Pha (phase)
Một chặng trong mỗi vòng event loop. Mỗi pha lo một loại macrotask.
Chặn event loop
Một đoạn code chạy lâu khiến event loop không lấy được việc khác ra chạy.

Event loop hoạt động thế nào

  1. Chạy hết code đồng bộ của file từ trên xuống, từng hàm một trên call stack.
  2. Việc phải chờ được giao đi: hẹn giờ, đọc file, gọi mạng đều được đăng ký với libuv. JS không đứng chờ.
  3. Xả microtask: khi call stack rỗng, Node chạy hết hàng nextTick, rồi hết hàng promise.
  4. Đi một vòng qua các pha: timers, poll (I/O), check (setImmediate)… ở mỗi pha chạy các callback đã sẵn sàng. Sau mỗi callback lại xả microtask.
  5. Lặp lại cho tới khi không còn việc gì chờ thì process thoát.

Các mục dưới đây đi sâu vào từng bước.

Call stack: nơi code đang chạy

Mỗi lần gọi một hàm, JS đặt hàm đó lên đỉnh call stack. Hàm chạy xong thì được lấy ra. JS chỉ chạy cái đang nằm trên đỉnh.

function tinhTien(soBuoi: number) { return soBuoi * 150_000; }
function inHoaDon() { console.log(tinhTien(8)); }
inHoaDon();
// Stack: [inHoaDon] → [inHoaDon, tinhTien] → [inHoaDon, console.log] → [] (rỗng)

Khi stack rỗng, JS rảnh, và event loop mới được lấy việc tiếp theo ra chạy.

Callback nằm ở đâu trong lúc chờ

Gọi setTimeout(fn, 100), Node không đứng đếm 100 ms. Nó đăng ký hẹn giờ với libuv rồi chạy tiếp dòng sau. Hết 100 ms, fn vào hàng đợi, nhưng chỉ được chạy khi stack rỗng và event loop đến pha timers. Vì vậy 100 ms là thời gian chờ tối thiểu. Trong Node, setTimeout(fn, 0) được tính thành 1 ms.

Macrotask và microtask

  • Macrotask: callback của timer, của I/O, của setImmediate. Mỗi loại được xử lý ở một pha.
  • Microtask: việc chạy ngay sau việc hiện tại. Node có hai hàng: process.nextTick, và promise (.then, code sau await, queueMicrotask).

Quy tắc quan trọng nhất: sau khi code đồng bộ chạy xong, và sau mỗi macrotask, Node xả hết hàng nextTick, rồi xả hết hàng promise. Microtask mới sinh ra trong lúc xả cũng được xả luôn. Chỉ khi cả hai hàng trống, event loop mới đi tiếp.

Làm thử: đoán thứ tự in ra

Đọc đoạn code, tự viết ra thứ tự bạn đoán, rồi mới chạy để so.

// order.cts, chạy: node order.cts
console.log('A: sync');
setTimeout(() => console.log('E: timeout'), 0);
Promise.resolve().then(() => console.log('C: promise'));
process.nextTick(() => console.log('D: nextTick'));
console.log('B: sync');
// In ra: A, B, D, C, E

Đổi tên file thành order.mts (ES module) thì C chạy trước D. Code top-level của ES module tự nó chạy trong một microtask, nên hàng promise được xả tiếp luôn. Bài học: đừng viết code phụ thuộc vào thứ tự giữa nextTick và promise.

setTimeout(fn, 0) và setImmediate(fn)

Gọi từ code chính của file: thứ tự không cố định. Gọi bên trong một callback I/O: setImmediate luôn chạy trước, vì lúc đó ta đang ở pha poll và pha kế tiếp là check.

import { readFile } from 'node:fs';
readFile(import.meta.filename, () => {
  setTimeout(() => console.log('timeout'), 0);
  setImmediate(() => console.log('immediate'));
  process.nextTick(() => console.log('nextTick'));
  Promise.resolve().then(() => console.log('promise'));
});
// Luôn in: nextTick, promise, immediate, timeout

process.nextTick: mạnh nhưng nguy hiểm

nextTick chạy ngay sau thao tác hiện tại, bất kể đang ở pha nào. Nếu một hàm tự gọi nextTick lặp mãi, hàng này không bao giờ trống, và timer với I/O không bao giờ được chạy. Hiện tượng này gọi là starvation. Tài liệu Node khuyên dùng setImmediate trong hầu hết trường hợp vì dễ đoán hơn.

Chặn event loop và cách phát hiện

Mỗi mili-giây luồng JS bận tính toán là một mili-giây mọi request khác phải chờ. Thủ phạm hay gặp: JSON.parse chuỗi rất lớn, regex bị backtracking, vòng lặp trên hàng trăm nghìn phần tử, hàm *Sync trong handler. Cách đo là xem độ trễ của event loop:

import { monitorEventLoopDelay } from 'node:perf_hooks';
const h = monitorEventLoopDelay({ resolution: 20 });
h.enable();
setInterval(() => {
  console.log(`p99 event loop delay: ${(h.percentile(99) / 1e6).toFixed(1)} ms`);
  h.reset();
}, 5000);

Với front-end developer: bạn đã biết cảm giác giao diện đơ khi một vòng lặp nặng chạy. Trên server, cái đơ đó xảy ra với tất cả người dùng cùng lúc.

Bút đỏ: những câu nghe đúng mà sai

"setTimeout(fn, 0) chạy ngay."Sai. Nó chạy sớm nhất ở pha timers của vòng sau, sau toàn bộ code đồng bộ và microtask.

"Promise chạy trên luồng khác."Sai. Hàm truyền vào new Promise chạy đồng bộ ngay. Chỉ .then mới chạy sau, dưới dạng microtask.

"nextTick chạy ở vòng event loop sau."Sai, dù cái tên gợi ý vậy. Nó chạy ngay sau thao tác hiện tại. setImmediate mới là cái chạy lượt sau.

Tự kiểm tra

Tự trả lời trước, rồi mới bấm mở đáp án.

console.log('1'); setTimeout(() => console.log('2'), 0); Promise.resolve().then(() => console.log('3')); console.log('4'); in ra gì?

1, 4, 3, 2. Code đồng bộ chạy trước (1, 4), rồi microtask (3), rồi mới tới hẹn giờ (2).

setTimeout(fn, 100) có chắc chắn chạy đúng sau 100 ms không?

Không. 100 ms là thời gian chờ tối thiểu. Nếu luồng JS đang bận một việc nặng, fn phải chờ việc đó xong.

Cả server chậm với mọi người dùng cùng lúc, database vẫn nhanh. Nghi ngờ đầu tiên là gì?

Event loop bị chặn bởi một đoạn code chạy lâu trên luồng chính. Đo bằng monitorEventLoopDelay.

Câu hỏi phỏng vấn

Giải thích event loop trong một phút.

JS trong Node chạy trên một luồng. Việc chờ như timer hay I/O được giao cho libuv và hệ điều hành; khi xong, callback vào hàng đợi. Event loop đi qua các pha theo thứ tự timers, poll cho I/O, check cho setImmediate, và ở mỗi pha chạy các callback đã sẵn sàng. Sau mỗi callback, Node xả hết microtask, trước là nextTick rồi tới promise. Vì chỉ có một luồng, một callback chạy lâu sẽ chặn tất cả việc khác.

Microtask và macrotask khác nhau thế nào?

Macrotask là callback xử lý theo pha: setTimeout, I/O, setImmediate. Microtask chạy ngay sau tác vụ hiện tại: promise, queueMicrotask, nextTick. Microtask luôn được xả hết trước macrotask kế tiếp, nên Promise.resolve().then(f) chạy trước setTimeout(g, 0).

setImmediate và setTimeout(fn, 0) khác gì?

setImmediate chạy ở pha check, ngay sau poll. setTimeout chạy ở pha timers. Trong callback I/O, setImmediate luôn chạy trước. Ở code chính thì thứ tự không được đảm bảo.

API thỉnh thoảng chậm 2 giây với mọi người. Bạn điều tra thế nào?

Mọi request cùng chậm gợi ý event loop bị chặn, không phải database chậm. Đo độ trễ event loop bằng monitorEventLoopDelay, chạy profiler (node --cpu-prof hoặc DevTools qua node --inspect) để tìm hàm chiếm CPU, rồi kiểm tra các thủ phạm quen thuộc: hàm *Sync, JSON.parse dữ liệu lớn, regex, vòng lặp lớn. Sửa bằng cách chia nhỏ việc, chuyển sang worker_threads, hoặc đưa ra hàng đợi công việc.

Nhớ 3 ý

  1. JS chạy một việc mỗi lúc; event loop chọn việc tiếp theo khi call stack rỗng.
  2. Thứ tự: code đồng bộ, rồi microtask (nextTick, promise), rồi macrotask theo pha (timers, I/O, setImmediate).
  3. Một callback chạy lâu chặn tất cả mọi người. Đo độ trễ event loop để phát hiện.
