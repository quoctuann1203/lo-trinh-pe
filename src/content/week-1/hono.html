Trong một câu

Web framework là bộ khung viết sẵn phần việc lặp đi lặp lại của một server: nhận request, tìm đúng hàm để xử lý, rồi gửi response về. Hono là một web framework nhỏ, nhanh, viết bằng TypeScript, dùng để viết API trên Node.js.

Hình dung một quán ăn: server là cả quán, request là phiếu gọi món, framework là quy trình của quán (ai nhận phiếu, phiếu nào chuyển cho bếp nào), còn handler là đầu bếp nấu đúng một món.

Vì sao cần framework

Node.js đã có sẵn module node:http để mở server. Nhưng nó chỉ đưa bạn request thô. Thử viết một API chỉ có một đường dẫn /health:

import { createServer } from 'node:http';
createServer((req, res) => {
  if (req.method === 'GET' && req.url === '/health') {
    res.writeHead(200, { 'Content-Type': 'application/json' });
    res.end(JSON.stringify({ ok: true }));
  } else {
    res.writeHead(404).end();
  }
}).listen(3000);

Một đường dẫn đã mất 8 dòng. API sách có 5 đường dẫn, mỗi cái cần đọc tham số trên URL, đọc body JSON, kiểm tra API key, trả lỗi đúng mã. Viết tay hết thì code thành một khối if/else rất dài, dễ sai và khó test.

Framework làm sẵn ba việc đó, để bạn chỉ viết phần riêng của sản phẩm:

  1. Routing: chọn hàm nào xử lý request nào.
  2. Middleware: chạy code chung trước và sau mọi request, như kiểm tra đăng nhập, ghi log.
  3. Tiện ích: đọc tham số, đọc body, trả JSON chỉ bằng một dòng.

Từ khoá cần biết

Request
Yêu cầu trình duyệt hay app gửi tới server. Gồm method (GET, POST…), đường dẫn (/books/42), header và có thể có body.
Response
Câu trả lời server gửi về. Gồm mã trạng thái (200, 404…), header và body.
Route
Một cặp "method + đường dẫn" gắn với một hàm xử lý. Ví dụ GET /books/:id.
Handler
Hàm xử lý một route: nhận request, trả response. Đầu bếp nấu đúng một món.
Context (c)
Object Hono truyền vào mỗi handler. Chứa request (c.req) và các hàm tạo response (c.json, c.text).
Middleware
Hàm chạy chen giữa request và handler. Dùng cho việc chung của nhiều route: kiểm tra API key, ghi log, đo thời gian.
Runtime
Môi trường chạy JavaScript: Node.js, Bun, Deno, Cloudflare Workers. Hono chạy được trên tất cả.

Hono xử lý một request thế nào

Khi có request GET /books/42 tới, Hono đi qua bốn bước:

  1. Tìm route. Hono so method và đường dẫn với danh sách route bạn đã khai báo, thấy GET /books/:id khớp, và ghi nhớ id = "42".
  2. Chạy middleware. Các middleware khớp với đường dẫn chạy lần lượt theo thứ tự khai báo. Middleware nào cũng có thể dừng lại và trả response luôn, ví dụ trả 401 khi thiếu API key.
  3. Chạy handler. Handler đọc id, tìm sách, gọi c.json(book) để tạo response.
  4. Đi ngược ra. Response đi qua các middleware theo chiều ngược lại, rồi mới gửi về trình duyệt. Nhờ vậy middleware ghi log biết được request mất bao lâu và trả mã gì.

Hono khác các framework cũ ở chỗ nó dùng chính Request và Response chuẩn của Web, là hai thứ bạn đã gặp khi gọi fetch ở front-end. Cả app chỉ là một hàm nhận Request, trả Response. Vì vậy cùng một đoạn code chạy được trên Node, Bun, Deno hay Cloudflare Workers.

Làm thử: API đầu tiên trong 5 phút

Bước 1. Tạo project, chọn template nodejs khi được hỏi:

npm create hono@latest hello-hono
cd hello-hono
npm install

Bước 2. Mở src/index.ts, thay bằng:

import { serve } from '@hono/node-server';
import { Hono } from 'hono';

const app = new Hono();

// Route 1: GET /health
app.get('/health', (c) => c.json({ ok: true }));

// Route 2: GET /books/:id, phần :id là tham số
app.get('/books/:id', (c) => {
  const id = c.req.param('id');
  return c.json({ id, title: `Sách số ${id}` });
});

serve({ fetch: app.fetch, port: 3000 });

Bước 3. Chạy npm run dev, rồi mở một cửa sổ terminal khác:

curl localhost:3000/health
# {"ok":true}

curl localhost:3000/books/42
# {"id":"42","title":"Sách số 42"}

curl -i localhost:3000/khong-co
# HTTP/1.1 404 Not Found

Bạn vừa có hai route mà không phải tự so URL hay tự gọi JSON.stringify. Đường dẫn không có route thì Hono tự trả 404.

const books = new Hono();
books.get('/', listBooks);        // GET /books
books.get('/:id', getBook);       // GET /books/42
app.route('/books', books);

Middleware: thứ tự chạy

Middleware nhận hai thứ: context c và hàm next. Code trước await next() chạy trên đường vào, code sau chạy trên đường ra:

app.use(async (c, next) => { console.log('A vào'); await next(); console.log('A ra'); });
app.use(async (c, next) => { console.log('B vào'); await next(); console.log('B ra'); });
app.get('/x', (c) => { console.log('handler'); return c.text('ok'); });
// GET /x in ra: A vào, B vào, handler, B ra, A ra

Middleware muốn chặn request thì trả response luôn, không gọi next(). Đây chính là cách làm kiểm tra API key:

import { createMiddleware } from 'hono/factory';
type Env = { Variables: { teacherId: string } };

const requireAuth = createMiddleware<Env>(async (c, next) => {
  if (c.req.header('x-api-key') !== 'secret') {
    // Dừng ở đây: handler không bao giờ chạy
    return c.json({ error: { code: 'UNAUTHENTICATED', message: 'Thiếu hoặc sai API key' } }, 401);
  }
  c.set('teacherId', 't-1');
  await next();
});

const app = new Hono<Env>();
app.use('/invoices/*', requireAuth);
app.get('/invoices', (c) => c.json({ teacherId: c.get('teacherId') }));

Xử lý lỗi ở một chỗ

Thay vì mỗi handler tự try/catch và tự chọn mã lỗi, handler chỉ cần throw. app.onError bắt mọi lỗi, kể cả lỗi trong hàm async, rồi quyết định trả gì. app.notFound lo đường dẫn không tồn tại.

app.onError((err, c) => {
  if (err instanceof AppError) {
    return c.json({ error: { code: err.code, message: err.message, details: err.details } }, err.status);
  }
  console.error('[unexpected]', err);   // ghi log đầy đủ cho mình xem
  return c.json({ error: { code: 'INTERNAL', message: 'Lỗi máy chủ' } }, 500);   // người dùng không thấy chi tiết
});

Được bốn lợi ích: mọi lỗi cùng một định dạng cho front-end, một chỗ ghi log, một chỗ chặn chi tiết nội bộ lọt ra ngoài, và handler ngắn hơn.

Tách ba lớp: route, service, store

Khi API lớn dần, đừng nhét hết vào handler. Chia làm ba lớp, mỗi lớp chỉ lo một việc:

LớpLo việc gìKhông cần biết
RouteHTTP: đọc request, validate, chọn mã trạng tháiDữ liệu lưu ở đâu
ServiceQuy tắc nghiệp vụ: ISBN không trùng, hoá đơn đã trả không được sửaHTTP
StoreĐọc, ghi dữ liệu (Map bây giờ, PostgreSQL ở tuần 5)Quy tắc nghiệp vụ

Lợi ích thấy ngay ở tuần 5: đổi từ Map sang PostgreSQL chỉ phải sửa lớp store, route và service giữ nguyên.

Bút đỏ: những câu nghe đúng mà sai

"Middleware chỉ chạy trước handler."Sai. Code sau await next() chạy sau handler và sửa được response.

"Thứ tự app.use không quan trọng."Sai. Middleware chạy theo thứ tự khai báo. Kiểm tra đăng nhập phải đứng trước route nó bảo vệ.

"Lưu user đăng nhập vào biến toàn cục cho tiện."Sai. Nhiều request chạy xen kẽ sẽ ghi đè nhau. Dùng c.set và c.get.

Tự kiểm tra

Tự trả lời trước, rồi mới bấm mở đáp án.

Route GET /books/:id nhận request GET /books/abc. c.req.param('id') trả gì?

Chuỗi "abc". Tham số trên đường dẫn luôn là chuỗi; muốn số thì tự chuyển và kiểm tra (bài zod).

Có hai middleware A rồi B, và B trả 401 mà không gọi next(). Handler có chạy không? A có chạy phần "ra" không?

Handler không chạy. A vẫn chạy phần sau await next(), vì response 401 của B đi ngược ra qua A.

Một handler throw new AppError(...). Ai biến lỗi đó thành response?

app.onError. Handler không cần try/catch.

Câu hỏi phỏng vấn

Middleware là gì? Thứ tự chạy ra sao?

Hàm nằm giữa request và handler, nhận context và next. Chạy theo thứ tự khai báo trên đường vào, ngược lại trên đường ra. Có thể dừng chuỗi bằng cách trả response luôn, như middleware xác thực trả 401.

Vì sao gom xử lý lỗi về một chỗ?

Để mọi lỗi cùng định dạng và cùng cách ghi log, để chi tiết nội bộ không lọt ra ngoài, và để handler ngắn. Handler ném lỗi có kiểu; một onError quyết định mã và nội dung trả về.

Hono khác Express thế nào?

Hono dựa trên chuẩn Request/Response của Web nên chạy trên nhiều runtime, viết bằng TypeScript từ đầu, và test được bằng app.request() không cần mở cổng. Express dùng req/res riêng của Node, hệ sinh thái lâu đời hơn, mô hình middleware tương tự.

Vì sao tách route, service, repository?

Để mỗi lớp chỉ có một lý do thay đổi. Đổi database không đụng quy tắc nghiệp vụ, và quy tắc nghiệp vụ test được riêng, nhanh, không cần server.

Nhớ 3 ý

  1. Framework lo phần lặp lại của server: routing, middleware, tiện ích đọc request và tạo response.
  2. Request đi vào qua từng middleware tới handler, response đi ra theo chiều ngược lại. Middleware trả response sớm để chặn request.
  3. Handler chỉ throw, app.onError lo biến lỗi thành response. Code chia ba lớp route, service, store.
