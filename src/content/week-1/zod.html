Ranh giới tin cậy

Những cửa vào cần kiểm tra: body, path param, query, header; biến môi trường; webhook của ngân hàng hay cổng thanh toán; response của API bên ngoài; file tải lên. Validate ở front-end giúp trải nghiệm tốt hơn. Validate ở server mới là bảo vệ thật, vì ai cũng gọi thẳng API được bằng curl.

Schema vừa kiểm tra vừa sinh kiểu

import * as z from 'zod';

const PaymentInput = z.object({
  studentId: z.uuid(),
  amount: z.number().int().positive(),            // VND, số nguyên
  method: z.enum(['cash', 'transfer']),
  note: z.string().max(200).optional(),
});
type PaymentInput = z.infer<typeof PaymentInput>;
// { studentId: string; amount: number; method: 'cash' | 'transfer'; note?: string }
  • .optional() cho phép thiếu, .nullable() cho phép null, .default(x) thiếu thì dùng x.
  • parse sai thì ném ZodError. safeParse không ném, trả { success, data } hoặc { success, error }.
  • z.flattenError(err) cho { formErrors, fieldErrors }, hợp với form phẳng. z.prettifyError(err) cho chuỗi dễ đọc để ghi log.

Trường lạ và lỗ hổng mass assignment

z.object mặc định bỏ mọi trường không khai báo:

PaymentInput.parse({ studentId: '...', amount: 600000, method: 'transfer', paid: true, role: 'admin' });
// → { studentId: '...', amount: 600000, method: 'transfer' }   paid và role bị bỏ

Nếu bạn ghi nguyên body vào database, kẻ xấu tự gửi thêm paid: true được. Lỗi này gọi là mass assignment. z.strictObject từ chối trường lạ, z.looseObject giữ trường lạ.

coerce cho query string

Query string luôn là chuỗi. z.coerce.number() đổi '5' thành 5. Body JSON đã đúng kiểu, đừng dùng coerce cho body.

Quy tắc liên trường và biến đổi

const Term = z.object({ start: z.iso.date(), end: z.iso.date() })
  .refine((v) => v.end >= v.start, { message: 'Ngày kết thúc phải sau ngày bắt đầu', path: ['end'] });

const Slug = z.string().trim().toLowerCase().transform((s) => s.replace(/\s+/g, '-'));
Slug.parse('  Dế Mèn Phiêu Lưu  '); // 'dế-mèn-phiêu-lưu'

Validate biến môi trường khi khởi động

const Env = z.object({
  PORT: z.coerce.number().int().default(3000),
  DATABASE_URL: z.url(),
  NODE_ENV: z.enum(['development', 'test', 'production']).default('development'),
});
export const env = Env.parse(process.env); // sai là sập ngay khi khởi động

Thiếu DATABASE_URL thì nên sập ngay với thông báo rõ ràng, thay vì lỗi lúc 2 giờ sáng khi có request đầu tiên cần database. Cách làm này gọi là fail fast.

Bút đỏ: những câu nghe đúng mà sai

"Có TypeScript rồi thì không cần validate."Sai. Kiểu bị xoá khi chạy. body as Book chỉ là hứa với trình biên dịch.

"z.coerce.boolean() đọc ?paid=false thành false."Sai. Nó dùng Boolean(x), nên chuỗi 'false' thành true. Dùng z.stringbool().

"PATCH dùng CreateSchema.partial() là xong."Coi chừng: .partial() vẫn giữ .default(). tags: .default([]) sẽ ghi đè tags thành [] mỗi lần PATCH.

Câu hỏi phỏng vấn

Đã dùng TypeScript, sao còn cần zod?

TypeScript chỉ kiểm tra lúc biên dịch, kiểu bị xoá khi chạy. Dữ liệu từ request là unknown. zod kiểm tra dữ liệu thật lúc chạy và suy ra kiểu từ cùng một schema, nên kiểu và bộ kiểm tra không lệch nhau.

Validate ở client hay server?

Cả hai, vì hai mục đích. Client để phản hồi ngay cho người dùng. Server để bảo vệ dữ liệu, và đây là lớp bắt buộc. Với TypeScript hai phía có thể dùng chung schema.

Mass assignment là gì, phòng thế nào?

Server ghi nguyên object client gửi vào database, khiến client tự đặt được trường chỉ server được đặt như role, paid. Phòng bằng cách chỉ nhận trường đã khai báo: zod tự bỏ trường lạ, hoặc dùng strictObject.

Vì sao validate biến môi trường lúc khởi động?

Để cấu hình sai làm deploy thất bại ngay với thông báo rõ ràng, thay vì server chạy rồi hỏng ở request đầu tiên. Code bên trong dùng env.PORT đã có kiểu.
