Trong một câu

Validate là kiểm tra dữ liệu từ bên ngoài gửi vào có đúng dạng không trước khi dùng. zod là thư viện giúp bạn mô tả "dữ liệu đúng trông thế nào" một lần, rồi dùng mô tả đó vừa để kiểm tra lúc chạy, vừa để TypeScript biết kiểu.

Hình dung bảo vệ ở cổng trường kiểm tra thẻ học sinh. Ai không có thẻ, thẻ sai tên, hay thẻ hết hạn thì không vào. Bên trong trường, thầy cô không phải hỏi lại "em có phải học sinh không". zod là người bảo vệ ở cổng API.

Vì sao phải validate ở server

TypeScript chỉ kiểm tra lúc bạn viết code. Khi chạy, kiểu bị xoá hết, và dữ liệu từ request có thể là bất cứ thứ gì: thiếu trường, số âm, chuỗi thay vì số, hay thêm trường lạ như paid: true. Ai cũng gọi thẳng API được bằng curl, không cần qua form của bạn. Validate ở front-end chỉ giúp người dùng thấy lỗi sớm; validate ở server mới là bảo vệ thật.

Những cửa vào cần kiểm tra: body, tham số trên đường dẫn, query, header; biến môi trường; webhook của ngân hàng hay cổng thanh toán; response của API bên ngoài; file tải lên.

Từ khoá cần biết

Validate
Kiểm tra dữ liệu có đúng quy tắc không, trước khi dùng.
Schema
Bản mô tả dữ liệu đúng: có những trường nào, mỗi trường kiểu gì, giới hạn gì.
parse
Kiểm tra theo schema. Đúng thì trả dữ liệu đã làm sạch; sai thì ném ZodError.
safeParse
Như parse nhưng không ném lỗi, trả { success, data } hoặc { success, error }.
z.infer
Lấy kiểu TypeScript ra từ schema, để khỏi viết kiểu hai lần.
Coerce
Ép kiểu, ví dụ chuỗi '5' thành số 5. Cần cho query string vì query luôn là chuỗi.
Mass assignment
Lỗ hổng khi server ghi nguyên object client gửi vào database, để client tự đặt trường như role, paid.

zod kiểm tra dữ liệu thế nào

  1. Viết schema một lần: trường nào, kiểu gì, giới hạn gì.
  2. Nhận dữ liệu thô từ request. Lúc này coi nó là unknown, chưa tin.
  3. Gọi parse hoặc safeParse: zod đi qua từng trường, so với schema.
  4. Sai thì nhận danh sách lỗi theo từng trường để trả 400 hoặc 422. Đúng thì nhận object sạch: trường lạ bị bỏ, kiểu đã chắc chắn.

Dùng trong API: schema vừa kiểm tra vừa sinh kiểu

import * as z from 'zod';

const PaymentInput = z.object({
  studentId: z.uuid(),
  amount: z.number().int().positive(),            // VND, số nguyên
  method: z.enum(['cash', 'transfer']),
  note: z.string().max(200).optional(),
});
type PaymentInput = z.infer<typeof PaymentInput>;
// { studentId: string; amount: number; method: 'cash' | 'transfer'; note?: string }
  • .optional() cho phép thiếu, .nullable() cho phép null, .default(x) thiếu thì dùng x.
  • parse sai thì ném ZodError. safeParse không ném, trả { success, data } hoặc { success, error }.
  • z.flattenError(err) cho { formErrors, fieldErrors }, hợp với form phẳng. z.prettifyError(err) cho chuỗi dễ đọc để ghi log.

Trường lạ và lỗ hổng mass assignment

z.object mặc định bỏ mọi trường không khai báo:

PaymentInput.parse({ studentId: '...', amount: 600000, method: 'transfer', paid: true, role: 'admin' });
// → { studentId: '...', amount: 600000, method: 'transfer' }   paid và role bị bỏ

Nếu bạn ghi nguyên body vào database, kẻ xấu tự gửi thêm paid: true được. Lỗi này gọi là mass assignment. z.strictObject từ chối trường lạ, z.looseObject giữ trường lạ.

coerce cho query string

Query string luôn là chuỗi. z.coerce.number() đổi '5' thành 5. Body JSON đã đúng kiểu, đừng dùng coerce cho body.

Quy tắc liên trường và biến đổi

const Term = z.object({ start: z.iso.date(), end: z.iso.date() })
  .refine((v) => v.end >= v.start, { message: 'Ngày kết thúc phải sau ngày bắt đầu', path: ['end'] });

const Slug = z.string().trim().toLowerCase().transform((s) => s.replace(/\s+/g, '-'));
Slug.parse('  Dế Mèn Phiêu Lưu  '); // 'dế-mèn-phiêu-lưu'

Validate biến môi trường khi khởi động

const Env = z.object({
  PORT: z.coerce.number().int().default(3000),
  DATABASE_URL: z.url(),
  NODE_ENV: z.enum(['development', 'test', 'production']).default('development'),
});
export const env = Env.parse(process.env); // sai là sập ngay khi khởi động

Thiếu DATABASE_URL thì nên sập ngay với thông báo rõ ràng, thay vì lỗi lúc 2 giờ sáng khi có request đầu tiên cần database. Cách làm này gọi là fail fast.

Làm thử: để zod bắt lỗi giúp bạn

Trong một thư mục trống: npm init -y, npm i zod, rồi tạo file thu.mjs:

import * as z from 'zod';

const Book = z.object({
  title: z.string().min(1),
  price: z.number().int().positive(),
});

console.log(Book.parse({ title: 'Dế Mèn', price: 50000, hack: true }));
// { title: 'Dế Mèn', price: 50000 }   trường lạ "hack" bị bỏ

const r = Book.safeParse({ title: '', price: -1 });
console.log(r.success);                       // false
console.log(z.flattenError(r.error).fieldErrors);
// { title: [ '...' ], price: [ '...' ] }     mỗi trường sai một danh sách lỗi

Chạy node thu.mjs. Thử đổi price thành chuỗi '50000' và xem zod báo gì.

Bút đỏ: những câu nghe đúng mà sai

"Có TypeScript rồi thì không cần validate."Sai. Kiểu bị xoá khi chạy. body as Book chỉ là hứa với trình biên dịch.

"z.coerce.boolean() đọc ?paid=false thành false."Sai. Nó dùng Boolean(x), nên chuỗi 'false' thành true. Dùng z.stringbool().

"PATCH dùng CreateSchema.partial() là xong."Coi chừng: .partial() vẫn giữ .default(). tags: .default([]) sẽ ghi đè tags thành [] mỗi lần PATCH.

Tự kiểm tra

Tự trả lời trước, rồi mới bấm mở đáp án.

Đã có type Book = { title: string }, viết const b = body as Book. Vì sao chưa an toàn?

as chỉ là lời hứa với TypeScript, không kiểm tra gì lúc chạy. Body thật vẫn có thể thiếu title.

Query ?page=2. Schema z.number() có nhận không?

Không, vì query luôn là chuỗi '2'. Dùng z.coerce.number().

Client gửi thêm role: 'admin' vào body đăng ký. Schema z.object không khai báo role. Chuyện gì xảy ra?

zod bỏ trường role, nên dữ liệu ghi xuống không có nó. Muốn từ chối hẳn request thì dùng z.strictObject.

Câu hỏi phỏng vấn

Đã dùng TypeScript, sao còn cần zod?

TypeScript chỉ kiểm tra lúc biên dịch, kiểu bị xoá khi chạy. Dữ liệu từ request là unknown. zod kiểm tra dữ liệu thật lúc chạy và suy ra kiểu từ cùng một schema, nên kiểu và bộ kiểm tra không lệch nhau.

Validate ở client hay server?

Cả hai, vì hai mục đích. Client để phản hồi ngay cho người dùng. Server để bảo vệ dữ liệu, và đây là lớp bắt buộc. Với TypeScript hai phía có thể dùng chung schema.

Mass assignment là gì, phòng thế nào?

Server ghi nguyên object client gửi vào database, khiến client tự đặt được trường chỉ server được đặt như role, paid. Phòng bằng cách chỉ nhận trường đã khai báo: zod tự bỏ trường lạ, hoặc dùng strictObject.

Vì sao validate biến môi trường lúc khởi động?

Để cấu hình sai làm deploy thất bại ngay với thông báo rõ ràng, thay vì server chạy rồi hỏng ở request đầu tiên. Code bên trong dùng env.PORT đã có kiểu.

Nhớ 3 ý

  1. Dữ liệu từ bên ngoài luôn là unknown; validate ở server mới là bảo vệ thật.
  2. Một schema zod vừa kiểm tra lúc chạy, vừa sinh kiểu TypeScript bằng z.infer.
  3. zod bỏ trường lạ để chống mass assignment; query cần coerce; biến môi trường validate ngay khi khởi động.
