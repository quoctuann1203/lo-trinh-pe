Object Error

Một Error có message, name và stack (các hàm đang chạy lúc lỗi được tạo, kèm file và dòng). Luôn ném new Error(...). throw 'hết hàng' không có stack, đọc log sẽ không biết lỗi từ đâu.

Ba con đường

Kiểu lỗiĐi đâuAi bắt được
throw đồng bộNgược lên call stacktry/catch gần nhất
Promise rejectTheo chuỗi promise.catch(), hoặc try/catch quanh await
emit('error', err)Tới listener 'error'emitter.on('error'). Không có listener thì Node ném lỗi ra ngoài

Lỗi trong callback của timer hay I/O không thuộc call stack ban đầu. Khi callback chạy, hàm đã gọi setTimeout kết thúc từ lâu, nên try/catch bên ngoài không bắt được.

Khi không ai bắt

  • unhandledRejection: promise reject mà không có .catch hay await. Từ Node 15, Node in lỗi và thoát với mã 1.
  • uncaughtException: lỗi đồng bộ đi hết call stack mà không gặp try/catch. Process sập.
try {
  loadStudent('');        // quên await: try/catch KHÔNG bắt được
} catch {
  console.log('không bao giờ in dòng này');
}
// → process in lỗi và thoát với mã 1

Có thể gắn process.on('uncaughtException') để process không sập, nhưng đừng chạy tiếp như không có gì. Lỗi có thể đã xảy ra giữa chừng một thao tác. Ghi log đầy đủ rồi thoát, để Docker, systemd hay Kubernetes khởi động lại một bản sạch.

Lớp lỗi riêng và cause

class PaymentGatewayError extends Error {
  constructor(message: string, options?: { cause?: unknown }) {
    super(message, options);
    this.name = 'PaymentGatewayError';
  }
}

try {
  await taoMaQR(hoaDon);
} catch (err) {
  throw new PaymentGatewayError(`Không tạo được mã QR cho hóa đơn ${hoaDon.id}`, { cause: err });
}

Tắt server an toàn

Khi deploy bản mới, hệ thống gửi SIGTERM cho process cũ. Thoát ngay thì request đang dở bị cắt ngang. Với thanh toán, đó có thể là tiền đã về nhưng chưa gạch nợ. Tắt an toàn: ngừng nhận request mới, chờ request đang chạy xong, đóng database, rồi mới thoát.

const server = serve({ fetch: app.fetch, port: 3000 });

process.on('SIGTERM', () => {
  server.close(() => {             // chờ request đang chạy xong
    // await db.end();
    process.exit(0);
  });
  setTimeout(() => process.exit(1), 10_000).unref(); // quá 10 giây thì buộc thoát
});

Bút đỏ: những câu nghe đúng mà sai

"Bọc try/catch quanh mọi thứ cho chắc."Sai. Catch mà không biết xử lý gì là giấu lỗi. Để lỗi nổi lên chỗ xử lý chung.

"catch (e) { console.log(e) } là đã xử lý lỗi."Sai. Request vẫn chạy tiếp với dữ liệu hỏng, hoặc client chờ mãi không có response.

"Server sập là thảm hoạ, phải chặn bằng mọi giá."Không hẳn. Với lỗi lập trình, sập rồi khởi động lại an toàn hơn chạy tiếp với trạng thái hỏng.

Câu hỏi phỏng vấn

uncaughtException và unhandledRejection khác nhau thế nào?

uncaughtException là lỗi đồng bộ đi hết call stack mà không gặp try/catch. unhandledRejection là promise reject mà không ai .catch hay await. Từ Node 15, cả hai mặc định làm process thoát.

Bạn viết gì trong process.on('uncaughtException')?

Ghi log đầy đủ kèm stack, gửi lên hệ thống theo dõi lỗi nếu có, rồi thoát với mã khác 0. Không chạy tiếp, vì trạng thái process có thể đã hỏng. Khởi động lại là việc của trình quản lý process.

Lỗi vận hành và lỗi lập trình khác gì?

Lỗi vận hành là tình huống đoán được dù code đúng, như email sai định dạng hay database timeout; xử lý bằng 4xx hoặc thử lại. Lỗi lập trình là bug, như đọc thuộc tính của undefined; sửa code, lúc chạy thì trả 500 và log.

Graceful shutdown là gì, vì sao cần?

Khi nhận SIGTERM, server ngừng nhận kết nối mới, chờ request đang chạy xong, đóng tài nguyên, rồi thoát trong giới hạn thời gian. Nó tránh cắt ngang request khi deploy, nhất là với thanh toán.
