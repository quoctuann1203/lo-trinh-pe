Trong một câu

Xử lý lỗi là quyết định trước: khi một việc hỏng thì lỗi đi đâu, ai bắt nó, và người dùng nhận được gì. Trong Node, lỗi không được ai bắt sẽ làm cả server sập.

Hình dung bếp nấu hỏng một món. Đầu bếp phải báo lên (ném lỗi), quản lý quán quyết định (xin lỗi khách, làm lại, hoàn tiền). Tệ nhất là đầu bếp lặng lẽ bỏ món đó: khách ngồi chờ mãi mà không ai biết.

Vì sao phải xử lý lỗi cẩn thận

Ở front-end, một lỗi thường chỉ làm hỏng một nút bấm trên máy một người. Ở server, một lỗi không ai bắt làm process thoát, và mọi người dùng đang kết nối cùng mất kết nối. Còn lỗi bị "nuốt" (catch rồi bỏ qua) thì tệ theo cách khác: request chạy tiếp với dữ liệu hỏng, hoặc client chờ mãi không có câu trả lời.

Từ khoá cần biết

Error
Object mô tả lỗi, có message (nói gì sai), name (loại lỗi) và stack (lỗi xảy ra ở file nào, dòng nào).
Ném lỗi (throw)
Dừng hàm hiện tại và đẩy lỗi ngược lên cho hàm đã gọi nó.
Bắt lỗi (try/catch)
Bọc đoạn code có thể lỗi; lỗi xảy ra thì chạy vào nhánh catch.
Reject
Promise thất bại. Bắt bằng .catch() hoặc try/catch quanh await.
Process
Một chương trình Node đang chạy. Process thoát là server tắt.
SIGTERM
Tín hiệu hệ điều hành gửi để nhờ process tự tắt, ví dụ khi deploy bản mới.

Một lỗi đi đâu

  1. Lỗi được tạo bằng throw new Error(...), hoặc một promise bị reject.
  2. Lỗi đi ngược lên: qua từng hàm đã gọi (call stack), hoặc theo chuỗi promise.
  3. Gặp chỗ bắt (try/catch, .catch, app.onError) thì dừng lại ở đó và được xử lý.
  4. Không gặp chỗ bắt nào thì Node in lỗi ra và thoát process với mã 1.

Luôn ném new Error(...), đừng ném chuỗi như throw 'hết hàng': chuỗi không có stack, đọc log sẽ không biết lỗi từ đâu.

Lỗi trong callback của timer hay I/O không thuộc call stack ban đầu. Khi callback chạy, hàm đã gọi setTimeout kết thúc từ lâu, nên try/catch bên ngoài không bắt được.

Khi không ai bắt

  • unhandledRejection: promise reject mà không có .catch hay await. Từ Node 15, Node in lỗi và thoát với mã 1.
  • uncaughtException: lỗi đồng bộ đi hết call stack mà không gặp try/catch. Process sập.
try {
  loadStudent('');        // quên await: try/catch KHÔNG bắt được
} catch {
  console.log('không bao giờ in dòng này');
}
// → process in lỗi và thoát với mã 1

Có thể gắn process.on('uncaughtException') để process không sập, nhưng đừng chạy tiếp như không có gì. Lỗi có thể đã xảy ra giữa chừng một thao tác. Ghi log đầy đủ rồi thoát, để Docker, systemd hay Kubernetes khởi động lại một bản sạch.

Lớp lỗi riêng và cause

class PaymentGatewayError extends Error {
  constructor(message: string, options?: { cause?: unknown }) {
    super(message, options);
    this.name = 'PaymentGatewayError';
  }
}

try {
  await taoMaQR(hoaDon);
} catch (err) {
  throw new PaymentGatewayError(`Không tạo được mã QR cho hóa đơn ${hoaDon.id}`, { cause: err });
}

Tắt server an toàn

Khi deploy bản mới, hệ thống gửi SIGTERM cho process cũ. Thoát ngay thì request đang dở bị cắt ngang. Với thanh toán, đó có thể là tiền đã về nhưng chưa gạch nợ. Tắt an toàn: ngừng nhận request mới, chờ request đang chạy xong, đóng database, rồi mới thoát.

const server = serve({ fetch: app.fetch, port: 3000 });

process.on('SIGTERM', () => {
  server.close(() => {             // chờ request đang chạy xong
    // await db.end();
    process.exit(0);
  });
  setTimeout(() => process.exit(1), 10_000).unref(); // quá 10 giây thì buộc thoát
});

Làm thử: ba cách lỗi thoát khỏi tay bạn

Tạo file loi.mjs, chạy lần lượt từng đoạn (comment hai đoạn kia) bằng node loi.mjs, rồi xem terminal in gì và process có thoát không.

// Đoạn 1: try/catch bắt được lỗi đồng bộ
try { JSON.parse('{'); } catch (e) { console.log('bắt được:', e.message); }

// Đoạn 2: lỗi trong setTimeout, try/catch bên ngoài KHÔNG bắt được
try { setTimeout(() => { throw new Error('trong timer'); }, 10); }
catch { console.log('không bao giờ in'); }

// Đoạn 3: promise reject không ai bắt
Promise.reject(new Error('không ai catch'));

Kết quả mong đợi: đoạn 1 in "bắt được" và chạy tiếp. Đoạn 2 và 3 in lỗi đỏ và process thoát với mã 1 (kiểm bằng echo $? ngay sau đó).

Bút đỏ: những câu nghe đúng mà sai

"Bọc try/catch quanh mọi thứ cho chắc."Sai. Catch mà không biết xử lý gì là giấu lỗi. Để lỗi nổi lên chỗ xử lý chung.

"catch (e) { console.log(e) } là đã xử lý lỗi."Sai. Request vẫn chạy tiếp với dữ liệu hỏng, hoặc client chờ mãi không có response.

"Server sập là thảm hoạ, phải chặn bằng mọi giá."Không hẳn. Với lỗi lập trình, sập rồi khởi động lại an toàn hơn chạy tiếp với trạng thái hỏng.

Tự kiểm tra

Tự trả lời trước, rồi mới bấm mở đáp án.

try { loadStudent(''); } catch {} mà loadStudent là hàm async bị lỗi. Lỗi có bị bắt không?

Không, vì thiếu await. Hàm trả promise rồi thoát khỏi try ngay; promise reject sau đó thành unhandledRejection. Viết await loadStudent('').

Người dùng gửi email sai định dạng. Đây là lỗi vận hành hay lỗi lập trình? Trả mã gì?

Lỗi vận hành: đoán trước được dù code đúng. Trả 4xx (400 hoặc 422) kèm thông báo rõ ràng.

Vì sao không nên để process chạy tiếp sau uncaughtException?

Lỗi có thể xảy ra giữa chừng một thao tác, trạng thái process đã hỏng. Ghi log rồi thoát, để trình quản lý khởi động lại bản sạch.

Câu hỏi phỏng vấn

uncaughtException và unhandledRejection khác nhau thế nào?

uncaughtException là lỗi đồng bộ đi hết call stack mà không gặp try/catch. unhandledRejection là promise reject mà không ai .catch hay await. Từ Node 15, cả hai mặc định làm process thoát.

Bạn viết gì trong process.on('uncaughtException')?

Ghi log đầy đủ kèm stack, gửi lên hệ thống theo dõi lỗi nếu có, rồi thoát với mã khác 0. Không chạy tiếp, vì trạng thái process có thể đã hỏng. Khởi động lại là việc của trình quản lý process.

Lỗi vận hành và lỗi lập trình khác gì?

Lỗi vận hành là tình huống đoán được dù code đúng, như email sai định dạng hay database timeout; xử lý bằng 4xx hoặc thử lại. Lỗi lập trình là bug, như đọc thuộc tính của undefined; sửa code, lúc chạy thì trả 500 và log.

Graceful shutdown là gì, vì sao cần?

Khi nhận SIGTERM, server ngừng nhận kết nối mới, chờ request đang chạy xong, đóng tài nguyên, rồi thoát trong giới hạn thời gian. Nó tránh cắt ngang request khi deploy, nhất là với thanh toán.

Nhớ 3 ý

  1. Lỗi đi ngược lên tới chỗ bắt gần nhất; không ai bắt thì process thoát.
  2. Lỗi vận hành (input sai, timeout) trả 4xx; lỗi lập trình (bug) sửa code, lúc chạy trả 500 và ghi log.
  3. Khi nhận SIGTERM: ngừng nhận request mới, chờ request đang chạy xong, rồi mới thoát.
