Trong một câu

Ràng buộc (constraint) là quy tắc bạn khai báo ngay trên bảng để database tự từ chối dữ liệu sai: giá không được âm, ISBN không được trùng, sách phải có tên. Dù code có bug, dữ liệu xấu vẫn không vào được bảng.

Hình dung khuôn làm bánh: bột đổ vào khuôn nào thì ra hình khuôn đó, không thể ra hình khác. Kiểu dữ liệu và ràng buộc là cái khuôn của mỗi cột.

Vì sao kiểm ở database khi đã có zod

zod kiểm dữ liệu đi qua API. Nhưng dữ liệu còn vào database qua nhiều đường khác: script nhập dữ liệu, một API khác viết sau, một lần sửa tay trong psql, hay một bug quên gọi validate. Ràng buộc ở database là lớp bảo vệ cuối, đúng với mọi đường vào.

Ràng buộc hoạt động thế nào

  1. Bạn khai báo ràng buộc trong CREATE TABLE.
  2. Mỗi lần INSERT hay UPDATE, database kiểm tra dòng mới với mọi ràng buộc.
  3. Vi phạm một cái thì cả câu lệnh bị từ chối, kèm thông báo nói rõ ràng buộc nào. Không có dòng nào được ghi dở.
  4. App bắt lỗi đó và trả mã phù hợp, ví dụ trùng ISBN thì 409 (học ở tuần 5).

Chọn kiểu dữ liệu

Kiểu dữ liệu là ràng buộc đầu tiên: cột date không bao giờ chứa được chữ "hôm qua". Bảng dưới đây đủ dùng cho hầu hết bảng của một web app.

Vì sao tiền không dùng số thực: SELECT 0.1::double precision + 0.2 ra 0.30000000000000004. Cộng hàng nghìn hoá đơn, sai số dồn lại thành tiền lệch. Đồng Việt Nam không có phần lẻ nên bigint là đủ và chính xác tuyệt đối.

Vì sao dùng timestamptz: nó lưu một thời điểm tuyệt đối (bên trong là UTC) và tự đổi sang múi giờ của phiên khi hiển thị. timestamp chỉ lưu "15 giờ ngày 3", không biết là 15 giờ ở đâu. Server đặt ở Singapore, người dùng ở Hà Nội, bạn sẽ không muốn đoán.

Schema sách có ràng buộc

-- sql/02-schema.sql
DROP TABLE IF EXISTS reviews, books, authors;

CREATE TABLE authors (
  id   bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name text NOT NULL CHECK (length(trim(name)) > 0),
  born integer CHECK (born BETWEEN 1000 AND 2100)
);

CREATE TABLE books (
  id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  author_id  bigint REFERENCES authors (id),          -- được NULL: sách chưa rõ tác giả
  isbn       text UNIQUE,
  title      text NOT NULL CHECK (length(trim(title)) > 0),
  year       integer CHECK (year BETWEEN 1450 AND 2100),
  price      integer NOT NULL CHECK (price >= 0),
  tags       text[] NOT NULL DEFAULT '{}',
  created_at timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE reviews (
  id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  book_id    bigint NOT NULL REFERENCES books (id) ON DELETE CASCADE,
  rating     smallint NOT NULL CHECK (rating BETWEEN 1 AND 5),
  body       text,
  created_at timestamptz NOT NULL DEFAULT now()
);

Vài điều đáng để ý:

  • DROP TABLE liệt kê bảng con trước bảng cha, vì reviews trỏ tới books, books trỏ tới authors.
  • CHECK coi NULL là qua. born là NULL thì không vi phạm BETWEEN. Muốn bắt buộc có giá trị thì thêm NOT NULL.
  • UNIQUE cho phép nhiều dòng cùng NULL, vì hai giá trị chưa biết không được coi là bằng nhau. Nhiều sách chưa có ISBN là hợp lệ.

Làm thử: 5 lệnh INSERT sai

Nạp vài tác giả và sách hợp lệ trước, rồi chạy từng lệnh dưới đây. Chép thông báo lỗi của mỗi lệnh vào notes và gạch chân tên ràng buộc trong đó.

INSERT INTO books (title, price) VALUES (NULL, 50000);
-- null value in column "title" of relation "books" violates not-null constraint

INSERT INTO books (title, price) VALUES ('Sách âm tiền', -1);
-- new row for relation "books" violates check constraint "books_price_check"

INSERT INTO books (title, price, isbn) VALUES ('Bản trùng', 1000, '978-0132350884');
-- duplicate key value violates unique constraint "books_isbn_key"

INSERT INTO books (title, price, author_id) VALUES ('Sách ma', 1000, 999);
-- insert or update on table "books" violates foreign key constraint "books_author_id_fkey"

INSERT INTO reviews (book_id, rating) VALUES (1, 6);
-- new row for relation "reviews" violates check constraint "reviews_rating_check"

Lệnh thứ ba chỉ báo lỗi nếu đã có sách mang ISBN đó, nên hãy thêm Clean Code với ISBN này trong dữ liệu mẫu. Tên ràng buộc do Postgres tự đặt theo mẫu bảng_cột_loại. Tuần 5, API sẽ đọc tên này để đổi lỗi database thành mã HTTP: unique thành 409, foreign key thành 422.

Bút đỏ: những câu nghe đúng mà sai

"Đã validate bằng zod ở API rồi, database không cần ràng buộc nữa."Cần cả hai. zod cho người dùng lỗi dễ hiểu sớm. Ràng buộc chặn mọi đường ghi khác: script nhập dữ liệu, code mới quên validate, hai request chạy song song.

"Kiểm tra email chưa tồn tại bằng SELECT rồi mới INSERT là đủ chống trùng."Không. Hai request cùng SELECT, cùng thấy chưa có, cùng INSERT. Chỉ ràng buộc UNIQUE chặn được.

"Lưu tiền bằng float cho tiện tính toán."Số thực có sai số làm tròn. Tiền dùng bigint theo đơn vị nhỏ nhất, hoặc numeric.

Tự kiểm tra

Tự trả lời trước, rồi mới bấm mở đáp án.

Muốn chắc giá sách không bao giờ âm, dù ai ghi vào bảng. Dùng ràng buộc gì?

CHECK (price >= 0) trên cột price.

Hai cuốn sách cùng ISBN được ghi vào bảng. Thiếu ràng buộc gì?

UNIQUE trên cột isbn.

Một lệnh INSERT 3 dòng, dòng thứ 2 vi phạm CHECK. Bao nhiêu dòng được ghi?

Không dòng nào: cả câu lệnh bị từ chối.

Câu hỏi phỏng vấn

Đã validate ở ứng dụng thì có cần ràng buộc trong database không?

Có. Validate ở ứng dụng để báo lỗi thân thiện và sớm. Ràng buộc trong database là bảo đảm cuối cùng, áp cho mọi đường ghi dữ liệu kể cả script và code tương lai, và là cách duy nhất chống trùng khi nhiều request chạy song song. Hai lớp này bổ sung cho nhau, không thay thế nhau.

Bạn lưu tiền bằng kiểu gì, vì sao?

Với tiền tệ không có phần lẻ như đồng Việt Nam, tôi dùng bigint theo đơn vị đồng. Với tiền có phần lẻ thì bigint theo đơn vị nhỏ nhất như cent, hoặc numeric với số chữ số cố định. Không dùng float hay double vì sai số làm tròn, cũng không dùng kiểu money của Postgres vì nó phụ thuộc cấu hình ngôn ngữ của server.

timestamp và timestamptz khác nhau thế nào?

timestamptz lưu một thời điểm tuyệt đối, bên trong là UTC, và hiển thị theo múi giờ của phiên kết nối. timestamp chỉ lưu ngày giờ không kèm múi giờ, nên không biết đó là giờ ở đâu. Với thời điểm sự kiện xảy ra như lúc thanh toán, luôn dùng timestamptz.

ON DELETE CASCADE nguy hiểm ở chỗ nào?

Một lệnh DELETE nhỏ có thể xoá dây chuyền rất nhiều dữ liệu ở các bảng khác mà người viết không để ý. Tôi chỉ dùng CASCADE khi dòng con hoàn toàn vô nghĩa nếu thiếu dòng cha, như các dòng chi tiết của một đơn hàng nháp. Với dữ liệu tài chính như hoá đơn, tôi để mặc định chặn xoá và dùng xoá mềm.

Nhớ 3 ý

  1. Ràng buộc là quy tắc trên bảng; database tự từ chối dữ liệu sai, dù đến từ đường nào.
  2. Năm loại hay dùng: NOT NULL, UNIQUE, CHECK, PRIMARY KEY, FOREIGN KEY.
  3. zod bảo vệ API, ràng buộc bảo vệ dữ liệu; cần cả hai.
